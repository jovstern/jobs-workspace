## Phase Goal

**As a** job seeker, **I want to** see what is missing and what to learn next, and to recover cleanly when the AI or my saved data fails, **so that** every fit check leaves me with a next step.

<objective>
Server half of "a distinct, retryable message for a failure, a timeout, a rate limit and an
unconfigured AI service": the part that decides which failure happened. Today every upstream
failure leaves the server as `ai_failed`, and a missed deadline cannot be told from the browser
leaving. After this plan each cause leaves the server as its own code, with the HTTP status,
retry flag and fixed sentence that plan 01.1-09 gave that code.

Purpose: FIT-11 and the server side of review finding WR-06. The browser can only word a failure
correctly, and offer Try again only when it helps, if the server says what happened.

Output: the AI client throws the code for each failure through `failureToErrorCode`, keeps its
deadline signal and splits finish reasons; a second fixed-token search in the diagnostics;
stand-in scenarios for every failure; the existing tests that pinned `ai_failed` updated in the
same tasks.

Split from the code contract (revision of 2026-10-12, scope): the codes, their statuses and retry
flags, the shared sentence table and the pure `failureToErrorCode` are plan 01.1-09, which this
plan depends on. This plan adds no error code and changes no file under `shared/`; under
`server/src/http/` it changes one test file only.

Decisions made here under "Claude's Discretion" (how failures are produced in tests): every
failure comes from a stand-in scenario or from closing the stand-in, and nothing is added to the
app server. The exact set of codes was decided in plan 01.1-09. The two browser-only codes
(`server_unreachable`, `request_timeout`) are plan 01.1-08. The browser's fit panel is unchanged by
this plan: it keeps showing its Phase 1 generic sentence for every code until plan 01.1-08, so
the browser gates stay green.
</objective>
