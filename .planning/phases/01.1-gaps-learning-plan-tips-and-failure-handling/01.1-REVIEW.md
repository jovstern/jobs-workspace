# Phase 01.1: Code Review Report

**Reviewed:** 2026-10-12
**Depth:** standard
**Files Reviewed:** 37
**Status:** issues_found

## Summary

No blockers. The project hard rules hold in the reviewed code:

- **Stateless server, no logging of resume, body or model output.** The only server log lines on the fit path are `formatFailureLine` (HTTP status number plus a category from a closed list) and the request log (method, path, status, duration). `client.ts` discards every thrown error and keeps only the `diagnoseError` output. `diagnose.ts` reads the error message only through fixed `includes(...)` token checks and never copies it. `AppError` messages come from the fixed `ERROR_MESSAGES` table, and `errorHandler` never echoes a thrown message.
- **Score computed in code.** The model schema (`fitModelOutputSchema`) has no score field. The page derives score and band through `computeFit` in `buildFitView` and stores neither.
- **No derived status stored.** Gaps, `hasAdvice` and the band are derived per render. This phase does not touch the applications store.
- **API key.** `GEMINI_API_KEY` is read only in `server/` (the spike script uses `loadServerEnv`). Spike output carries ids, enum values and numbers only.
- **Rendering of model text.** Plan steps, quotes, tips and keywords are rendered as plain text. There is no `dangerouslySetInnerHTML`. Advice is filtered item by item in code (links, platform names, quote verification, keywords must occur in the trusted posting).

The findings below are test reliability, robustness and consistency defects.

## Warnings

### WR-01: PasteForm test "removes an email address typed into the reviewed text and saves only on the next click" asserts on async work without waiting

**File:** `src/features/resume/PasteForm.test.tsx:162-174`
**Issue:** The test is racy in two places. Both depend on how fast the event loop drains after `user.click`, which is why it passes on rerun and fails under load.

1. Lines 164-166. After clicking Save, `form.handleSubmit()` runs asynchronously (TanStack Form validation, then `onSubmit`). Line 164 asserts `toHaveValue(...)` straight after the click, with no retry. Line 165 then does `await screen.findByRole('status')`. A status element already exists, left over from the first Review click (it says "We did not find an email address..."). So `findByRole` resolves at once with the stale element. The next one-shot `toHaveTextContent('...1 email address...')` can then run before the submit has updated the notice.
2. Line 172-174. The second Save click goes through `buildResumeRecord`, which awaits `sha256Hex` (WebCrypto), and only then calls `saveResume`. `user.click` does not wait for that. Line 174 reads `useResumeStore.getState().resume?.text` immediately. The last test in the file (line 186) already uses `vi.waitFor` for the same reason.

The "not yet saved" assertions at lines 169-170 (`resume` is null, `storedResume()` is null) can also pass vacuously if they run before the first submit has finished.

**Fix:** Wait on an observable outcome of the submit instead of reading synchronously. Minimal change:
```tsx
await user.click(screen.getByRole('button', { name: 'Save resume' }))

// Wait for the second pass to finish: the notice text changes only after onSubmit ran.
expect(
  await screen.findByText(/Removed before anything is sent to Google: 1 email address\./),
).toBeInTheDocument()
expect(field).toHaveValue(`${WITHOUT_CONTACTS}\n[email removed]`)
expect(screen.getByRole('button', { name: 'Save resume' })).toBeInTheDocument()
expect(useResumeStore.getState().resume).toBeNull()
expect(storedResume()).toBeNull()

await user.click(screen.getByRole('button', { name: 'Save resume' }))

await vi.waitFor(() => {
  expect(useResumeStore.getState().resume?.text).toBe(`${WITHOUT_CONTACTS}\n[email removed]`)
})
```
Do not use `findByRole('status')` here, because that element already exists before the second submit.

### WR-02: "Try again" resends the old resume text and ignores the panel's unavailable state

**File:** `src/features/fit-analysis/FitPanel.tsx:74-78`
**Issue:** `retry()` only guards on `isChecking` and on `checkFit.variables` existing. It then calls `checkFit.mutate(checkFit.variables)`, which carries the `resumeText` and `resumeHash` captured at the first click. Two consequences:
- If the user replaced or removed the resume after the failure, which is possible while the error notice stays on screen, Try again sends the old resume to Google. That is a paid call that sends text the user may have just deleted. The result is also stored under the old hash, so it is never shown as current.
- `startCheck` refuses to run when `reason !== undefined` (no resume, or `unavailableReason`), but `retry` does not. Try again therefore bypasses the unavailable state that disables Check my fit and Check again.

**Fix:** Reuse the same guard and send the current resume:
```tsx
function retry() {
  if (isUnavailable || resume === null) return
  holdFocus()
  checkFit.mutate({ jobId: job.id, resumeText: resume.text, resumeHash: resume.textHash })
}
```
`isUnavailable` already includes `isChecking`. This makes `startCheck(true)` and `retry` the same path, so you can call `startCheck(true)` directly.

### WR-03: A partly unreadable store is rewritten without its dropped entries even when no copy of them was kept

**File:** `src/lib/guarded-storage.ts:194-206`
**Issue:** The whole-value case is careful: `setAsideWhole` removes the original only if the copy was written. The partial case is not. When `result.droppedCount > 0` and `setAside` fails (`copyKept === false`, the usual cause being a full disk), the code still writes `{ state: result.state }` over the original. That permanently deletes the dropped entries, and the only record is a notice saying they were "left out". This is the same data-loss risk the whole-value path avoids. The notice wording ("A copy could not be kept") is honest, but the destruction is avoidable.

**Fix:** Rewrite only when the copy exists (or nothing was dropped):
```ts
const copyKept =
  result.droppedCount > 0
    ? setAside(storage, name, JSON.stringify({ state: result.dropped, version }))
    : true
if (result.droppedCount > 0) report({ store, kind: 'partial', copyKept, dropped: result.droppedCount })
if (copyKept && (migrated || result.droppedCount > 0)) {
  try { storage.setItem(name, JSON.stringify({ state: result.state, version })) }
  catch { report({ store, kind: 'write_failed', copyKept: false }) }
}
```
If the original is left in place, the `incident-line.ts` text for `partial` with `copyKept === false` ("left out") must change to match, for example "will be replaced the next time you save". Add a test with a storage whose `setItem` throws for `:corrupt:` keys.

### WR-04: Rating quotes are stored with no length bound

**File:** `server/src/fit/analyze.ts:50-63`, `shared/src/fit.ts:18-24`
**Issue:** The prompt asks for quotes of at most 25 words, but code never enforces it for ratings. `verifyQuote` accepts any span that occurs in the resume, up to the whole 60,000-character resume (or several 200-character-gap segments). `ratedRequirementSchema.quote` is `z.string().nullable()` with no max. A model that ignores the limit can write up to roughly 60 KB of resume per rating into the persisted `jw:analyses` store. That is a localStorage quota risk, and it shows resume text in large blocks in the gap blockquote. Tips already have a cap (`TIP_QUOTE_MAX_CHARS`), so the two are inconsistent.

**Fix:** In `settle`, treat an over-long quote like an unverifiable one:
```ts
if (rated.quote === null || rated.quote.length > QUOTE_MAX_CHARS || !verifyQuote(rated.quote, index)) {
  return notEvidenced(requirementId, '', true)
}
```
Also add `.max(QUOTE_MAX_CHARS)` to `ratedRequirementSchema.quote` (shared). Choose a value such as 600, to match `TIP_QUOTE_MAX_CHARS`. Note that a stored result whose quote exceeds the new max would then fail `storedAnalysisSchema` and be set aside. Choose a bound that existing synthetic results satisfy, or apply the cap on the server only.

## Info

### IN-01: Non-transient failures are marked retryable and offer "Try again"

**File:** `shared/src/error.ts`, `server/src/http/errors.ts:23`, `server/src/ai/failure-code.ts:22`
**Issue:** Any status that is not 401/402/403/429/5xx, with a category other than the listed ones, becomes `ai_failed` with `retryable: true`. This includes 400 INVALID_ARGUMENT (for example a rejected schema) and 404 NOT_FOUND (a wrong model id). `MODELS.fit.id` is a hand-set string, so a 404 is a plausible configuration error. The user is shown "Something went wrong on our side. Try again." with a button that can never succeed.
**Fix:** Map 400 and 404 to a non-retryable code, or to `ai_failed` with `retryable: false`, via a dedicated code such as `ai_misconfigured` with a message that points at the server config.

### IN-02: Any TypeError inside the model call is reported as a network failure

**File:** `server/src/ai/diagnose.ts:107-108`
**Issue:** `diagnoseError` maps every `TypeError` to the category `network`, which becomes `ai_network` ("Check your connection"). That is right for a failed `fetch`. A programming TypeError inside the `try` in `client.ts` (a bad response shape, a change in the SDK) would be mislabelled the same way and send the user off to check their connection.
**Fix:** Narrow the check, for example to `error.message === 'fetch failed'` or a `cause` with a network `code`. Alternatively keep it as is and accept that, since the error text cannot be kept.

### IN-03: Unused data and magic coupling

**File:** `src/features/fit-analysis/fit-errors.ts:15,47`, `shared/src/fit.ts:36`
**Issue:** `FitErrorView.action` has no consumer in this phase; the file's own comment says so. `PLANS_MAX = 10` is a hard-coded cap that must stay at or above the largest requirement count of any seed job. If a job ever had more than 10 gaps, `adviceSchema.safeParse` in `buildAdvice` would fail and silently discard all advice.
**Fix:** Either delete `action` until Phase 01.2 needs it, or add a test that renders it. Replace `PLANS_MAX` with a check against `job.requirements.length` (or add a seed-data test that asserts no job exceeds it).

### IN-04: Loose comparison and a timing-sensitive e2e assertion

**File:** `src/features/fit-analysis/FitPanel.tsx:81`, `e2e/check-fit.spec.ts:351-352`
**Issue:** `view?.score != null` uses loose inequality in a file that otherwise uses strict comparisons; write `view?.score !== undefined && view.score !== null`. The progress e2e test asserts `Reading your resume` is visible. The stand-in's slow scenario answers at 3 s and the stage line changes at 4 s. Under a loaded runner there is only a one-second margin between the click and that assertion.
**Fix:** For the first, tighten the comparison. For the second, lower the stand-in delay (`slowDelayMs`) for that scenario to about 1.5 s, or assert only on the heading and the progress bar.
