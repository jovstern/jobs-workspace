# Phase 01.1: Gaps, learning plan, tips and failure handling - Context

**Gathered:** 2026-10-11
**Status:** Ready for planning

<domain>
## Phase Boundary

A fit check now leaves the user with a next step. The result panel gains a Gaps section (split
required vs nice-to-have), a learning plan for every gap and resume tailoring tips. While a check
runs the user sees progress; when it fails they see a message specific to the failure, with
"Try again" only where retrying can help. Saved data that is corrupted or from an older version is
migrated or set aside with a visible notice, and the page keeps working.

Requirements: FIT-04, FIT-06, FIT-07, FIT-11, DATA-02.

Not in this phase: PDF upload, the structured profile, the two-step review, "I do have this",
replace or delete the resume and the "resume changed, re-check?" marker (all Phase 01.2); the
three-pane workspace and design system (Phase 2); export, import and erase, including getting a
set-aside copy back (Phase 7). Styling stays plain, as in Phase 1.

This phase reuses the Phase 1 planning files, which were written for the union of Phases 1, 01.1
and 01.2: `01-CONTEXT.md`, `01-RESEARCH.md`, `01-UI-SPEC.md`, `01-PATTERNS.md` and
`01-VALIDATION.md`. Decision ids below are local to this phase and are written `D-E01` to `D-E10` so they
cannot be confused with Phase 1's `D-` ids, which still apply.

</domain>

<decisions>
## Implementation Decisions

### Learning plan (FIT-06)
- **D-E01:** "What to learn" is **2 to 4 short steps per gap, one line each**, shown as a numbered
  list. It is not a single sentence. This replaces the single `whatToLearn` string sketched in
  `01-RESEARCH.md` B.1 with a list of steps. The other two fields are unchanged: "Why it matters
  for this job" (one or two sentences) and "Rough effort" (days / weeks / months).
  — **Reversibility:** costly — the plan shape is part of the AI contract and is stored with every
  saved analysis; changing it later needs a storage migration and a prompt change
- **D-E02:** A **partial** gap's plan covers **only the difference** between what the resume shows
  and what the job asks (for example "you have REST, the job wants GraphQL"). It is usually
  shorter and its effort smaller than a plan for a requirement with no evidence. The prompt must
  say this explicitly.
- **D-E03:** **Every gap gets a plan**, required and nice-to-have, partial and not evidenced.
  Plans for required gaps are shown open. Plans for **nice-to-have gaps start collapsed** behind a
  "Show plan" control (keyboard operable, state announced), so a poor-fit result stays readable.
- **D-E04:** No links and no named courses, products-as-courses, or providers in any plan step
  (carried from Phase 1). Enforce in the prompt and strip or reject URLs in code.

### Tailoring tips (FIT-07)
- **D-E05:** Each "Emphasise what you already have" tip is a **quote from the resume plus advice**
  on how to emphasise it. The quote is **verified in code against the resume text**, with the same
  check used for rating quotes; a tip whose quote is not found is **dropped**, not shown without
  its quote. The AI **never writes resume wording** for the user: no suggested rewrites of a line.
- **D-E06:** "Words from the posting your resume does not use" are **proposed by the AI and
  filtered by code**: a keyword is kept only if it really appears in the posting text and really
  is absent from the resume text (case-insensitive, whole-word or whole-phrase). Shown as chips
  with the fixed note "Add only if true for you."
- **D-E07:** At most 5 emphasise tips and 8 keywords (as in `01-RESEARCH.md` B.1).

### Results saved before this phase
- **D-E08:** A stored analysis with no advice (every fit check run in Phase 1) is **kept and shown
  as it is**: score, ratings and the Gaps list (which is derived from the ratings and needs no
  AI). Where plans and tips would be, one notice says they are new and offers **Check again**.
  That is one ordinary fit check: it replaces the stored result, ratings included. Nothing runs
  until the user clicks. The result is **not** marked out of date, and there is **no** separate
  advice-only route or button.
  Copy: "Learning plans and tailoring tips are new. Check again to add them to this result."

### Corrupted saved data (DATA-02)
- **D-E09:** A set-aside copy is **only kept**, not offered for download and not restorable in
  this phase. Recovery is Phase 7. The notice copy in `01-UI-SPEC.md` ("A copy is kept in this
  browser.") stands.
- **D-E10:** Only the **most recent few set-aside copies per store** are kept (Claude picks the
  number; 3 is the working assumption), so repeated corruption cannot fill browser storage and
  block new saves.

### Carried forward from Phase 1 (already decided, do not re-ask)
- Gap wording, verbatim: "not evidenced in your resume"; for a partial: "partly evidenced in your
  resume". Section headings `Required gaps ({n})` / `Nice-to-have gaps ({n})`. A gap is any
  requirement not rated met. Gaps follow the posting's order; no model-made ranking.
- All copy for score, gaps, plan labels, the plan-missing line, tailoring headings, progress
  lines, the per-code error table and the storage notices is in `01-UI-SPEC.md` and is the
  contract, except where D-E01, D-E03 and D-E08 add to it.
- Errors branch on the typed `code`, never on message text. "Try again" appears only for
  retryable codes, repeats the same request on one click and is never automatic. A failed
  re-check keeps the previous result visible under the notice.
- One model call returns ratings and advice together. Split into two calls only if measured p90
  latency goes above about 15 seconds (`01-RESEARCH.md` B.1). Ratings alone measured p90 4.7 s at
  LOW thinking (`01-SPIKE-RESULTS.md`).
- The score is computed in code from the ratings and never depends on the advice. Advice that is
  missing or fails validation must never cost the user their ratings.
- A fit check starts only from a click. Never on render, selection, refresh, focus or a timer.
- Server stays stateless: route, status and duration in logs only. Synthetic resumes only.
- The "I do have this" button shown inside gap items in `01-UI-SPEC.md` is Phase 01.2. Do not
  render it in this phase.

### Folded in from the Phase 1 code review
- **WR-06** (`01-REVIEW.md`, `deferred-items.md`): the fit panel offers "Try again" for
  non-retryable failures. Fix as part of FIT-11. `forbidden_origin` gets its own message that
  points at the local setup, along the lines of "The app server refused this page's address. Open
  the app at http://localhost:5173 or set ALLOWED_ORIGINS."

### Claude's Discretion
- Whether advice comes in the same model call as the ratings, by the measured-latency rule above.
  A new live measurement needs a paid call, so it needs the user's go-ahead at that moment; the
  Phase 1 approval does not cover it.
- Thinking level, output cap and deadline for the larger response, and updating the "Usually 10
  to 20 seconds" reassurance to match what is measured.
- The timing of the three progress lines.
- How failures are produced in tests and in the demo (the stand-in model and stopping the server
  are the obvious tools). No test or demo may depend on the real model failing.
- The exact set of server error codes beyond the four the roadmap names (failure, timeout, rate
  limit, not configured), within the table in `01-UI-SPEC.md`.
- What "Edit resume" does for `ai_blocked` in this phase, given the review dialog is Phase 01.2
  (for example move focus to the paste form).
- Migration mechanics, the shared storage helper, the incident store behind the notice, whether a
  dismissed notice stays dismissed after a refresh, and how many set-aside copies are kept.
- How a plan that is missing for one gap is handled beyond the fixed line "No learning plan was
  generated for this one. Check again to try once more."

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `shared/src/fit.ts` — `fitResponseSchema` and `storedAnalysisSchema` carry `advice: z.null()`
  with `FIT_SCHEMA_VERSION = 1`. Phase 1 reserved the field so that widening it to
  "advice or null" needs no storage migration; old records stay valid with `advice: null` (D-E08).
- `server/src/ai/prompts/fit.ts` — `FIT_SYSTEM_INSTRUCTION`, `fitModelOutputSchema(ids)`,
  `buildFitUserTurn`, `FIT_PROMPT_VERSION = 'fit-ratings-1'`. The advice half is added here; the
  prompt version must change. The first line and the user-turn layout are parsed by the stand-in
  model and are marked as fixed.
- `server/src/fit/quotes.ts` — rating-quote verification; reuse for emphasise-tip quotes (D-E05).
- `server/src/test-support/fake-gemini.ts` — the stand-in model the real SDK talks to in CI and
  e2e. It must learn to return advice and to fail on demand.
- `server/src/ai/client.ts`, `server/src/ai/diagnose.ts`, `server/src/http/errors.ts` — the one
  AI client and error mapper. Today every upstream failure becomes `ai_failed`.
- `shared/src/error.ts` — `ERROR_CODES` (nine codes) and the envelope `{code, message,
  retryable}`. The wire `code` is a plain string so new codes do not break an older client.
- `src/lib/api.ts` — `ApiError` with `code` and `retryable`.
- `src/features/fit-analysis/FitPanel.tsx` — shows one generic message and always "Try again"
  except for `ai_not_configured`; one static progress line. `RequirementsSection.tsx`,
  `ScoreBlock.tsx`, `selectors.ts` (`buildFitView`, `selectCurrentAnalysis`) derive the view.
- `src/features/fit-analysis/fit-store.ts` (`jw:analyses`, version 1) and
  `src/features/resume/resume-store.ts` (`jw:resume`, version 1) — both `merge` functions
  validate with Zod and silently start empty on failure. Their comments name DATA-02 as the place
  where set-aside and the notice arrive. Neither has a `migrate` or a guarded storage adapter.
- `src/components/Notice.tsx`, `Button.tsx`, `Badge.tsx`, `Card.tsx` — existing primitives.
- `server/src/config/models.ts` — `MODELS.fit`: `gemini-3.8-flash`, LOW thinking, 4096 output
  tokens, 30 s deadline, all derived from the ratings-only response. Advice makes the response
  several times larger, so cap and deadline need revisiting.

### Established Patterns
- Derive, never store: gaps, score and band are computed in render from stored ratings.
- User-owned records are written from the mutation's success handler into persisted stores.
- One component per file, named exports, feature folders, tests beside the file.
- Paid calls are mutations with no retry and no implicit refetch.
- Model output schema uses only the JSON Schema subset Gemini documents (`server/src/ai/schema.ts`):
  flat, all fields required, nullable rather than optional, no string length bounds.

### Integration Points
- `POST /api/fit` (`server/src/fit/routes.ts`, `analyze.ts`) returns the response that gains
  advice.
- `src/App.tsx` is where the page-top `StorageNotice` mounts.
- `e2e/` with `playwright.config.ts` runs against the stand-in model unless `REAL_AI` is set;
  the demo GIF comes from these recordings.

## Specific Ideas

Layouts the user picked from previews:

```
Required gap
Experience with GraphQL APIs
not evidenced in your resume

What to learn
 1. Schema basics: types, queries, mutations
 2. Build a small API with pagination and auth
 3. Add a GraphQL client to an existing React project of yours

Why it matters for this job
 The team's product API is GraphQL-only.

Rough effort: weeks
```

```
Emphasise what you already have

 From your resume:
 | "Led migration of the checkout flow to React 18 with a 30% faster first paint"
 Move this to your first bullet and name the metric up front; the posting asks for
 performance work three times.
```

```
+------------------------------------------+
| Learning plans and tailoring tips are    |
| new. Check again to add them to this     |
| result.                  [ Check again ] |
+------------------------------------------+
```

Plan steps are things to do or learn, ending where possible in something the user can show.
They are never a course, a link or a product pitch.
