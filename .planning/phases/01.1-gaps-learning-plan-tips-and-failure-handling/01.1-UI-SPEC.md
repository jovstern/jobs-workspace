# Phase 01.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope of this contract (read first)

Phase 01.1 is the second of three phases split out of the original Phase 1. The approved contract `.planning/phases/01-real-ai-path-end-to-end/01-UI-SPEC.md` ("01-UI-SPEC") covers all three. **This file is the contract for Phase 01.1 on its own.** It carries forward, unchanged, what 01-UI-SPEC says about this phase's surfaces, and adds what decisions E-01 to E-10 (`01.1-CONTEXT.md`) and `01.1-RESEARCH.md` require.

**Surfaces in this phase**

1. The **Gaps** section of the fit result (required and nice-to-have), with a **learning plan** per gap.
2. The **Tailoring** section (emphasise tips, missing keywords).
3. The **notice on a result saved before this phase** (E-08).
4. **Progress** while a fit check runs.
5. **Failure messages** for every code the server or the browser can produce, and the retry rule (FIT-11, WR-06).
6. The **storage notice** for corrupted, newer or unwritable saved data (DATA-02).

**Not in this phase (Phase 01.2 or later). Do not build, render or leave a placeholder for any of these:**

- PDF upload, the unreadable-PDF consent panel, the review dialog and its two steps, the profile editor, `Modal` and `ConfirmDialog`.
- **The "I do have this" button** and its live region. **Gap items render no "I do have this" button in this phase**, and no "confirmed by you" marker, tip or "Remove confirmation" control.
- "Remove confirmation", the confirmed split line, the "resume changed, re-check?" stale marker and the **Re-check** label. The header re-run button is always **Check again** here.
- Replace or delete resume, "Edit resume" (the `ai_blocked` action exists as data only, see Errors).
- Download, restore or erase of a set-aside copy (Phase 7), the three-pane layout and the design system (Phase 2).

**Styling stays plain, as built in Phase 1.** No new token, font, colour, icon package or registry is introduced. Everything below uses values already in the 01-UI-SPEC tables.

Sources: `01.1-CONTEXT.md` (E-01..E-10, WR-06, carried decisions); `01.1-RESEARCH.md` Parts 2, 3, 4, 5, 7, 8, 9 and "Open Questions" item 2; `01-UI-SPEC.md` ("Score, bands, ratings", "Progress", "Errors", "Corrupted or failed storage", "Fit panel (result)" items 5 and 6, "Fit running", "Interaction and Accessibility"); `.claude/skills/stack-conventions/SKILL.md`; the code at `src/`.

**Copy marked "decided here"** was not fixed by CONTEXT or 01-UI-SPEC. It is listed together in "Copy decided in this contract" so plan approval can review it in one place.

## Spacing Scale

Carried unchanged from 01-UI-SPEC. Multiples of 4 only. Tailwind: `1=4px, 2=8px, 4=16px, 6=24px, 8=32px, 12=48px, 16=64px`. Do not use `3`, `5` or `.5` steps for padding, margin or gap.

| Token | Value | Tailwind | Used in this phase for |
|-------|-------|----------|------------------------|
| xs | 4px | `1` | Glyph-to-text gap |
| sm | 8px | `2` | Gap between chips; gap between lines inside a gap item; gap between plan label and its content |
| md | 16px | `4` | Plan block padding (`p-4`); gap between gap items; notice padding (existing) |
| lg | 24px | `6` | Indent of the numbered steps (`pl-6`); gap between tips |
| xl | 32px | `8` | Not used for new section spacing |
| 2xl | 48px | `12` | `mt-12` before the Requirements, Gaps and Tailoring headings |
| 3xl | 64px | `16` | Not used |

Exceptions (fixed dimensions, not spacing steps):

- Buttons are `min-h-11` (44px), as built.
- **The "Show plan" / "Hide plan" control uses the `link` button variant plus `min-h-6` (24px)**, the WCAG 2.2 AA minimum target size (SC 2.5.8), the same exception 01-UI-SPEC makes for chip buttons. The link variant has no minimum height by itself, so the class is required.
- Progress bar track `h-2` (8px). Borders 1px. Plan block and quote rule: `border-l-2` for quotes only. Focus outline 2px with 2px offset.

## Color

Carried unchanged: neutral Tailwind v4 default palette, no custom hex, no `@theme` token, no `dark:` variants. Dominant `gray-50` page with `white` text surfaces, secondary `white` + `border-gray-200` cards, accent `blue-700`, destructive `red-700`.

| Role | Value | Usage in this phase |
|------|-------|---------------------|
| Dominant (60%) | `gray-50` page, `white` card | Page; the job detail card |
| Secondary (30%) | `white`/`gray-50` surfaces with `border-gray-200` | Plan block (`bg-gray-50 border border-gray-200`, text `gray-900`, secondary text `gray-600`: 17.0:1 and 7.2:1 on `gray-50`) |
| Accent (10%) | `blue-700` (hover `blue-800`) | Reserved list below |
| Destructive | `red-700` | Not used in this phase. Danger **tint** (`red-50`/`red-800`) is used for error notices only |

Accent reserved for (explicit list, unchanged except item 5 names the new control):

1. The filled primary button: at most one visible per surface (**Check my fit**, shown only when there is no result).
2. The keyboard focus outline on every interactive element (`outline-blue-700`, 2px, offset 2px).
3. The selected job in the job list.
4. The active tab indicator (Phase 01.2).
5. Text-style buttons: **Show plan / Hide plan** (`blue-700`, underlined, 6.8:1 on white).
6. The Progress bar fill.

Accent is **not** used for gap phrases, plan blocks, chips, keyword chips, notices, ratings or scores.

Status tones (unchanged): the **E-08 notice is neutral** (`gray-800` on `gray-100`, border `gray-200`, 13.3:1); the **error notices are danger** (`red-800` on `red-50`, 7.7:1); the **storage notice is caution** (`amber-900` on `amber-50`, 8.8:1). ### Errors (FIT-11, WR-06; reconciled with RESEARCH Part 4.3)

Headline for every row: **Could not check your fit**. Branch on the typed `code`, never on message text. The message shown is looked up by `code` from one table in the browser (RESEARCH 5.2/5.3); the envelope `message` is never displayed. **Try again** appears **iff** the error's `retryable` flag is true (the server's flag, or `true` for the browser-only codes), never from a hard-coded list of codes. It repeats the same request on one click, is never automatic and is ignored while a check is running.

| `code` | Message | Retryable (button) | Source |
|--------|---------|--------------------|--------|
| `ai_not_configured` | AI is not set up. Add GEMINI_API_KEY to server/.env and restart the server. | no | 01-UI-SPEC, VERBATIM |
| `ai_auth_failed` | Google did not accept the AI key. Check GEMINI_API_KEY in server/.env and restart the server. | no | 01-UI-SPEC, VERBATIM |
| `ai_billing` | The Google project behind the key has no credit or billing set up. Fix it in Google AI Studio, then try again. | no | 01-UI-SPEC, VERBATIM |
| `ai_rate_limited` | Google's AI is rate limiting this key. Wait a while, then try again. If it keeps happening, a daily quota may be used up: check your usage in Google AI Studio. | yes | **decided here** (replaces "Wait a minute": Google sends the same 429 for a per-minute and a daily limit) |
| `ai_overloaded` | Google's AI is busy right now. Try again in a moment. | yes | 01-UI-SPEC |
| `ai_timeout` | The request took too long. Try again. | yes | 01-UI-SPEC |
| `request_timeout` (browser only, 60 s) | The request took too long. Try again. | yes | same copy as `ai_timeout` |

**Interim `ai_blocked` (Open Question 2).** 01-UI-SPEC's sentence ends "Edit your resume text and try again" with an "Edit resume" action. In this phase a saved resume cannot be edited, replaced or deleted (Phase 01.2), so the interim message names no action. It states what happened and what did not (nothing saved), and it is honest that the same check will not help. The page's own action (the header **Check again**) stays available, and a different job can be selected. The table entry carries `action: 'edit_resume'` as **data only**; **nothing renders for it in this phase**. Phase 01.2 changes this one entry: message back to "The AI declined to process this text. Edit your resume text and try again." and the **Edit resume** button on.

**A failed re-check keeps the previous result visible** under the error notice (the result block depends on the stored analysis, not on the failure). When a retry or a new check starts, the notice disappears and the progress shows; when it fails again the notice returns above the restored result.

## Layout and Structure

Structure is the contract; file and component names are suggestions (one component per file, named export, per stack rules).

### Fit panel (result), top to bottom, as it stands after this phase

1. Header row: `h2` "Your fit for {job title}"; right side the secondary button **Check again** (accessible name exactly "Check again").
2. Reason line (`text-sm text-gray-600`) when the check is unavailable, as built.
3. Status region, always mounted (see Progress).
4. Progress bar while running.
5. Error notice (danger, `role="alert"`) when the last check failed and none is running.
6. Result (not rendered while a check runs):
   1. Score block (unchanged).
   2. Requirements `h3` (unchanged apart from `mt-12`).
   3. **Gaps** `h3` (new).
   4. **Tailoring** `h3` (new; absent when `advice` is `null`).

Heading hierarchy inside the panel: `h2` panel; `h3` Requirements, Gaps, Tailoring; `h4` for every sub-group. The Notice's heading is a paragraph, as built.

### Gaps section

```
h3  Gaps                                            (tabIndex -1, mt-12)
    [E-08 notice]                                   (only when advice is null)
    -- or, when there are no gaps --
    "Every requirement is evidenced in your resume."
    h4  Required gaps (n)
        ol  one li per required gap, posting order
    h4  Nice-to-have gaps (n)
        ol  one li per nice-to-have gap, posting order
```

- A gap is any requirement whose rating is not `met`. The list is **derived in render** from the stored ratings and the job (never stored, never ranked, never sorted). The counts are the lengths of the two lists.
- Required and nice-to-have groups are separate `ol`s, each with `aria-labelledby` its `h4`. The `li`s have no visible list marker (`list-none`, the Tailwind default); the plan steps inside do.
- Gap items are separated by `gap-6` (24px).
- **There is no "I do have this" button, no live region for it and no confirmed marker in any gap item.**

### Gap item, required gap (plan open)

Top to bottom inside one `li` (`flex flex-col gap-2`):

1. Requirement text (Body, `text-gray-900`).
2. Gap phrase line: the glyph (`aria-hidden`) and the phrase (Small, 600).
3. **Partial only:** "From your resume:" (Small, `gray-600`) and the stored quote in a `blockquote` with the Requirements section's classes (`border-l-2 border-gray-300 pl-4 text-sm break-words text-gray-900`). Rendered only if the stored quote is not null. Not rendered for not-evidenced gaps.
4. The **plan block** (below) or the plan-missing line or nothing (see states).

### Plan block

A `div` with `flex flex-col gap-2 rounded border border-gray-200 bg-gray-50 p-4`:

1. **Partial only:** the lead-in line (Small, `gray-600`): "This plan covers only what your resume does not yet show."
2. Label "What to learn" (Label, `id` set), then an `ol` (`list-decimal pl-6 flex flex-col gap-1`, `aria-labelledby` the label id) of **1 to 4** steps in the order received, Body, one `li` per step. The AI is asked for 2 to 4; the server may deliver 1 (RESEARCH A6). Render exactly what arrives; do not pad, split or number-prefix text yourself.
3. Label "Why it matters for this job" (Label), then one paragraph (Body).
4. `Rough effort: {days|weeks|months}` (Small; "Rough effort:" at weight 600). One text node reading "Rough effort: weeks" for screen readers.

### Gap item, nice-to-have gap (plan collapsed by default; E-03)

Same items 1 to 3 as above (requirement, phrase, quote for a partial) are **always visible**. Item 4 is a Radix `Collapsible`:

```
<Collapsible.Root>                       closed on first render, uncontrolled
  <Collapsible.Trigger asChild>
    <Button variant="link" className="min-h-6 self-start" aria-label="Show plan: {requirement text}">Show plan</Button>
  </Collapsible.Trigger>
  <Collapsible.Content>  plan block  </Collapsible.Content>
</Collapsible.Root>
```

- **Label:** visible text is **Show plan** when closed and **Hide plan** when open. The accessible name carries the same verb plus the requirement text (`Show plan: {text}` / `Hide plan: {text}`), so two triggers in one list are never indistinguishable and the visible label is inside the name (label-in-name).
- **State announcement:** Radix sets `aria-expanded` (`false`/`true`) on the button and `aria-controls` while open. Keep both. The changed name is a deliberate redundancy so sighted users also see the state; do **not** add `aria-live` anywhere for this control.
- **Keyboard:** the trigger is a native `<button type="button">`: it takes Tab focus in reading order; **Enter** and **Space** toggle; no arrow-key handling and no Esc handling. Nothing in the plan is focusable.
- **Focus:** focus stays on the trigger when it opens and when it closes. It is never moved into the plan block.
- **Collapsed content is not rendered.** `Collapsible.Content` renders no children while closed (Radix default). **Do not use `forceMount`.** Consequences accepted: text in a closed plan is not found by the browser's find-in-page and is not read by screen readers until opened; component tests must click the trigger before asserting step text.
- **No animation.** No transition classes, no content-size variables (motion rule: only the progress pulse animates).
- **Open state is per item, in memory only.** It resets when the analysis is replaced: key the Gaps section on the analysis timestamp (`analysedAt`). A failed re-check re-mounts the result, so open plans close again; accepted.
- No `defaultOpen`, no "expand all", no persistence of open state.

| State of the gap | What renders |
|------------------|--------------|
| `advice` is `null` (result saved before this phase) | Items 1 to 3 only. **No plan block, no plan-missing line, no Show plan control** for any gap. The E-08 notice explains it |
| Advice present and a plan exists for this gap | Required gap: plan block open. Nice-to-have gap: the Collapsible |

For a nice-to-have gap there is **no Show plan control** (nothing to reveal). No button is added to the line: "Check again" in the sentence means the panel's header button |
| Advice present, no plan for **any** gap | Each gap shows its own plan-missing line. The lines are not merged |

### Tailoring section

```
h3  Tailoring your resume for this job              (mt-12)
    p   intro (Body)
    h4  Emphasise what you already have
    ul  tips  | or | p "Nothing specific to emphasise for this job."
    h4  Words from the posting your resume does not use
    p   "Add only if true for you."  (Small, gray-600; sits between the subheading and the chips)
    ul  keyword chips | or | p "No missing keywords found." (no note in this case)
```

- **Tip** (`li`, `flex flex-col gap-2`, tips separated by `gap-6`): "From your resume:" (Small, `gray-600`), then the quote in the same `blockquote` classes as Requirements, then the advice (Body). The quote is shown **without added quotation marks**; the blockquote's left rule marks it as a quote, exactly as in the Requirements section. Order is quote first, advice after (CONTEXT layout). The server has already verified every quote against the resume and dropped tips that failed (E-05); the browser renders what is stored and does no matching. The AI never writes replacement wording, so there is no "suggested rewrite" element.
- **Keyword chips:** `ul` with `flex flex-wrap gap-2`, `aria-labelledby` the keywords `h4`. Each chip is a **read-only `Chip`** (no button, not focusable, no tooltip, never a link): `rounded-full border border-gray-300 bg-white px-2 py-1 text-sm text-gray-900 break-words`. At most 8 are stored; the UI renders all it is given and adds no "show more".
- **Limits:** the server delivers at most 5 tips and 8 keywords (E-07). Zero tips and zero keywords are both normal.
- **Section states:**

| `advice` | `tailoring` | Renders |
|----------|-------------|---------|
| `null` | n/a | **Nothing** (no heading). The E-08 notice stands in for it |
| object | `null` | Heading, then only the line "Tailoring tips could not be generated for this check. Check again to try once more." (Small, `gray-600`). No intro, no subheadings |
| object | present, both lists empty | Heading, intro, both subheadings each with its empty line |
| object | present | Heading, intro, the two sub-sections; each sub-section independently shows its list or its empty line |

### Result saved before this phase: the notice (E-08)

- **When:** whenever the stored analysis for this job has `advice === null`, including a result with no gaps (tips are also missing). Never when `advice` is an object.
- **What it is:** the existing `Notice` with `tone="neutral"` and `role="status"`, no heading, containing one row: `div` `flex w-full flex-wrap items-center justify-between gap-4` holding the fixed sentence (`p`, Body) and a **secondary** `Button` with visible text **Check again**. The row wraps at narrow widths; the button stays visible. The notice is static content present at render, not a live announcement, and nothing is announced when it appears.
- **Where:** inside the Gaps section, **directly under the Gaps `h3`**, above the sub-groups or the "no gaps" line. Reason: that is where the plans would be, a heading-navigating screen reader reaches it after "Gaps", and it covers the tips as well because the Tailoring section is absent in this state.
- **Not stale:** the result is not marked out of date. Score, ratings, band and gaps show as normal.
- **Two buttons, two names.** The header button keeps the accessible name exactly "Check again". The notice button's visible text is "Check again" (fixed by CONTEXT) and its accessible name is `Check again to add learning plans and tips` via `aria-label`: it begins with the visible text, so label-in-name holds, and it is not identical to the header name. **Test rule:** Playwright's `getByRole('button', { name: 'Check again' })` is a substring match and would match both. Locate the header button with `exact: true` and the notice button by its full name. Component tests (Testing Library matches full strings) are unaffected, but the `advice: null` fixtures in `FitPanel.test.tsx` will now render the notice and need updating.
- **Behaviour:** both buttons run the same single ordinary fit check for the same job; it replaces the stored result, ratings included. Nothing runs until a click. Both are `aria-disabled` while a check is running or when the check is unavailable, with `aria-describedby` pointing at the existing reason line.
- **Focus after a click on the notice button:** the notice is removed from the page as soon as the check starts (the result is replaced by the progress), so the button that had focus disappears. On click, move focus to the **header Check again button**, which stays mounted (`aria-disabled`) through the run, and leave it there on success. The same rule applies to **Try again**: when the error notice is removed because a retry started, focus moves to the persistent action button (header **Check again** when a result exists, otherwise **Check my fit**). A failed run leaves focus on that button and the new alert is announced by its role.

### Fit running (progress)

Inline in the panel (no nested card). While a check for this job is pending:

- Heading text "Checking your fit" (`p`, Body 600), the stage line and the reassurance are shown with the bar.
- Radix `Progress` with no `value` (indeterminate), `aria-label="Checking your fit"`, fill `bg-blue-700 w-full animate-pulse motion-reduce:animate-none` in a `h-2 rounded-full bg-gray-200` track. With reduced motion the bar is a static full-width fill; the text still says what is happening.
- The result, the notice and the error notice are not rendered while running. The header **Check again** (or primary **Check my fit**) stays rendered and `aria-disabled`; its label does not change.
- **Live region (the screen-reader contract).** Exactly one `role="status"` region exists in the panel and it is **always mounted**. While running it contains **only the stage line** (one `p` that is never remounted, so an unchanged text is not re-announced on each one-second tick). The heading, the reassurance line and the bar are **outside** the region. After a successful check the same region contains the completion sentence, then is cleared. Outside a check it is `sr-only` and empty.
- **Announcement budget:** at most four announcements per check (the stage line appears; then at 4 s, 10 s and 30 s) plus one on completion. Changes are at least 4 s apart (thresholds 4, 10, 30). The elapsed time is never shown as a number and the one-second timer produces no text change by itself.
- On failure the region is emptied and the danger notice (`role="alert"`) announces the error; the two do not speak over each other.

### Error notice

Danger `Notice` (`role="alert"`), heading "Could not check your fit", the mapped message, and **Try again** (secondary button) only when retryable. It sits under the header and above the result, as built. It does not take focus. For `forbidden_origin` and the other non-retryable rows there is no button; the page's own action stays available.

### Storage notice

- **Placement:** first child of the page container (`mx-auto max-w-5xl px-6 py-8`), **above `header`**, with `mb-6`, rendered only when there is at least one incident. Present from the first render because the stores read storage at import, before React renders.
- **Anatomy:** caution `Notice`, `role="alert"`, no heading. A `ul` with one `li` per incident (Body, wrapping, `gap-2`), then one secondary **Dismiss** button. One button dismisses the whole notice.
- **Behaviour:** dismissal is in memory only. After a refresh it does not return, whether or not it was dismissed, because the bad value has already been moved aside. A later failed save may add a "Write failed" line again (one per store at a time).
- **Focus after Dismiss:** the notice is removed, so focus moves to the page `h1` ("Jobs Workspace"), which gets `tabIndex={-1}` for this purpose.
- **Announcement limit (accepted):** alerts that are already on the page at load are announced inconsistently by screen readers (RESEARCH A10). The notice is the first element in reading order and focus is not moved on load. Incidents that arrive later in the session (a failed save) mount a new alert and are announced normally.
- **The page keeps working:** after a set-aside, the affected store starts empty and every control behaves as for a first visit: resume unreadable shows the empty resume card and the paste form; fit checks unreadable shows the job list with **Check my fit** available.
- There is **no download, restore, export or erase control** and no mention of one (E-09).
