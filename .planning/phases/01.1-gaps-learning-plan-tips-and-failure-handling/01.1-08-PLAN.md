## Phase Goal

**As a** job seeker, **I want to** see what is missing and what to learn next, and to recover cleanly when the AI or my saved data fails, **so that** every fit check leaves me with a next step.

<objective>
Browser half of FIT-11. Plans 01.1-09 and 01.1-05 made the server say what went wrong; this plan makes the
page say it, offer Try again only when it can help (review finding WR-06), name a stopped app
server correctly, and show staged progress while a check runs. It ends with the one browser
test that drives the roadmap's demo flow for this phase.

Purpose: success criterion 4 ("progress while an analysis runs, and a distinct, retryable message
for a failure, a timeout, a rate limit and an unconfigured AI service"), and the recording the
demo GIF is made from.

Output: `fit-errors.ts` and `FitErrorNotice`; `progress-lines.ts` and `FitProgress`; `api.ts`
mapping a non-envelope 5xx and the browser timeout; the panel wired; browser tests for a
rate-limited check recovered with Try again, a stopped server, a refused address, a slow check,
and the demo flow.

Decisions made here under "Claude's Discretion": the browser-only code `request_timeout` for the
60-second browser timeout; the stage lines change at 4, 10 and 30 seconds (the UI contract's
decided timing); failures in browser tests come from the stand-in's scenarios and from
Playwright's `page.route`, never from the real model or a switch in the app server. The
`ai_blocked` entry carries `action: 'edit_resume'` as data and nothing is rendered for it.
</objective>

## Flagged assumptions

- **The stage lines describe typical progress by elapsed time.** They are not a report from the
  server, which sends nothing until the answer is complete. The UI contract accepted this and the
  wording is fixed there.
- **The completion sentence keeps its Phase 1 behaviour** (it stays in the hidden status region
  until the next check or until another job is opened). The UI contract's "then is cleared" is read
  as that existing behaviour, which Phase 1 verified.
- **The proxy's empty 502 is produced with `page.route` in the browser test**, not by stopping the
  server (research A12: the real proxy path was read in the installed Vite code, not run).
- **A timeout cannot be shown in a browser test without waiting for it**, so `ai_timeout` and
  `request_timeout` are proven by component tests with stubbed responses and by the server tests
  of plans 01.1-05 and 01.1-09.
- **The unconfigured-AI case is proven by a component test** and by the existing notice in the job
  detail: the browser-test server always has the stand-in's key.
- **Two status roles can be on the page at rest** (the panel's hidden region and the old-result
  notice from plan 01.1-02). Tests scope their queries; nothing is announced by the notice.
