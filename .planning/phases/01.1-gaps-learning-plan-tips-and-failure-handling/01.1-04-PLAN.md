## Phase Goal

**As a** job seeker, **I want to** see what is missing and what to learn next, and to recover cleanly when the AI or my saved data fails, **so that** every fit check leaves me with a next step.

<objective>
Saved data that is corrupted, half-corrupted, from an older version, from a newer version or
impossible to write no longer fails silently. It is migrated or set aside, the user is told in a
notice at the top of the page, and the page keeps working.

Purpose: DATA-02. Today both stores validate in Zustand's `merge` and quietly start empty; the
corrupt value is then overwritten by the next save. Research showed `merge` cannot tell "nothing
stored" from "garbage stored", so all detection moves into a custom storage's `getItem`.

Output: `createGuardedStorage` (one helper for both stores), an in-memory incident store,
`StorageNotice` mounted in `App`, both stores switched to the helper, and a browser spec that
corrupts storage, reloads and finds a notice above a working page.

Decisions made here under "Claude's Discretion": persist versions stay 1 and no migration runs
on real data in this phase (the runner is shipped and tested with injected fixtures); 3 set-aside
copies per store are kept (D-E10); dismissal is in memory only and a refresh does not bring the
notice back, because the bad value has already been moved.
</objective>

## Flagged assumptions

- **No migration runs on real data in this phase** (research A14). Both stores stay at persist
  version 1; the runner is exercised by injected fixtures only. A no-op "1 to 2" step added only
  to have a visible migration was considered and not planned.
- **A refresh before reading the notice loses it.** Dismissal and the incident list are in memory
  only; the copy stays in storage. Persisting an "acknowledged" flag was rejected because it is
  one more value that can itself be corrupted.
- **Alerts present at page load are announced inconsistently by screen readers** (research A10;
  accepted in the UI contract). The notice is the first element in reading order.
- **Set-aside copies can contain resume text** (already contact-free when the app saved it; a
  hand-edited value may contain anything). They stay in the same browser storage as the live
  data, at most 3 per store. Phase 7's "erase all" must remove every key that starts with `jw:`.
- **Two stores failing to write produce two identical lines** ("one per store at a time" in the
  UI contract). Accepted as written.
