### Locked Decisions

**Learning plan (FIT-06)**
- **D-E01:** "What to learn" is **2 to 4 short steps per gap, one line each**, shown as a numbered list. It is not a single sentence. This replaces the single `whatToLearn` string sketched in `01-RESEARCH.md` B.1 with a list of steps. The other two fields are unchanged: "Why it matters for this job" (one or two sentences) and "Rough effort" (days / weeks / months). Reversibility: costly, the plan shape is part of the AI contract and is stored with every saved analysis; changing it later needs a storage migration and a prompt change.
- **D-E02:** A **partial** gap's plan covers **only the difference** between what the resume shows and what the job asks (for example "you have REST, the job wants GraphQL"). It is usually shorter and its effort smaller than a plan for a requirement with no evidence. The prompt must say this explicitly.
- **D-E03:** **Every gap gets a plan**, required and nice-to-have, partial and not evidenced. Plans for required gaps are shown open. Plans for **nice-to-have gaps start collapsed** behind a "Show plan" control (keyboard operable, state announced), so a poor-fit result stays readable.
- **D-E04:** No links and no named courses, products-as-courses, or providers in any plan step (carried from Phase 1). Enforce in the prompt and strip or reject URLs in code.

**Tailoring tips (FIT-07)**
- **D-E05:** Each "Emphasise what you already have" tip is a **quote from the resume plus advice** on how to emphasise it. The quote is **verified in code against the resume text**, with the same check used for rating quotes; a tip whose quote is not found is **dropped**, not shown without its quote. The AI **never writes resume wording** for the user: no suggested rewrites of a line.
- **D-E06:** "Words from the posting your resume does not use" are **proposed by the AI and filtered by code**: a keyword is kept only if it really appears in the posting text and really is absent from the resume text (case-insensitive, whole-word or whole-phrase). Shown as chips with the fixed note "Add only if true for you."
- **D-E07:** At most 5 emphasise tips and 8 keywords (as in `01-RESEARCH.md` B.1).

**Results saved before this phase**
- **D-E08:** A stored analysis with no advice (every fit check run in Phase 1) is **kept and shown as it is**: score, ratings and the Gaps list (which is derived from the ratings and needs no AI). Where plans and tips would be, one notice says they are new and offers **Check again**. That is one ordinary fit check: it replaces the stored result, ratings included. Nothing runs until the user clicks. The result is **not** marked out of date, and there is **no** separate advice-only route or button. Copy: "Learning plans and tailoring tips are new. Check again to add them to this result."

**Corrupted saved data (DATA-02)**
- **D-E09:** A set-aside copy is **only kept**, not offered for download and not restorable in this phase. Recovery is Phase 7. The notice copy in `01-UI-SPEC.md` ("A copy is kept in this browser.") stands.
- **D-E10:** Only the **most recent few set-aside copies per store** are kept (Claude picks the number; 3 is the working assumption), so repeated corruption cannot fill browser storage and block new saves.

## Summary

Phase 1 was built as the research predicted for the ratings half, and it left the advice half cleanly reserved: `advice: z.null()` in the shared schema, a fixed prompt envelope, one AI client seam, a stand-in model that runs the real SDK over HTTP. That makes this phase mostly additive. Four things in the as-built code, found by reading it and by scratch runs, change the plan from what the Phase 1 research suggested:

1. **`client.ts` validates the model's whole answer with the same Zod schema it sends to Gemini.** A single malformed plan would therefore throw away the ratings (`schema_mismatch` becomes `ai_failed`). To keep the ratings, the client needs a second, lenient parse schema: ratings strict, advice parts `z.unknown()`, assembled afterwards by a pure function that cannot throw. Zod's `.catch()` is not an option: it emits `default`, which the allow-list test rejects [VERIFIED: scratch run].
2. **Every upstream failure is `ai_failed` today, and a missed deadline is indistinguishable from the browser leaving.** A deadline abort and a client abort both surface as `AbortError` with category `aborted` [VERIFIED: scratch run against the stand-in]. The only reliable timeout signal is the state of the `AbortSignal.timeout(...)` object, which `client.ts` creates inline and throws away. Everything else needed for the full code table (HTTP status, a closed category list, finish reasons) is already collected in `diagnose.ts`; the smallest change is one pure function from diagnostic to code.
3. **Zustand's `merge` cannot tell "nothing stored" from "garbage stored"**: it is called with `undefined` in both cases [VERIFIED: scratch run]. The Phase 1 sketch (`createJSONStorage` wrapper plus validating `merge`) therefore cannot reliably set data aside. Do the whole job inside a custom `PersistStorage.getItem` (parse, envelope check, migrate, validate, set aside, prune, report) and return an already-valid value. Verified to hydrate synchronously and to skip `migrate` [VERIFIED: scratch run].
4. **When the app server is down behind the Vite proxy, the browser gets HTTP 502 with an empty `text/plain` body, not a network error** [VERIFIED: node_modules/vite/dist/node/chunks/node.js:19936, quoting `res.writeHead(502, { "Content-Type": "text/plain" }).end()`; `preview` inherits `server.proxy` at :35632 `proxy: preview?.proxy ?? server.proxy`]. `src/lib/api.ts` currently turns that into `internal_error`, so `server_unreachable` ("Can't reach the app server") is never shown in the real setup. A non-envelope 5xx must map to `server_unreachable`.

**Primary recommendation:** Keep one model call (ratings, then plans, then tailoring, in that field order) at LOW thinking; raise the cap to 8192 tokens and the deadline to 45 s as a safe default that needs no paid call; separate the provider schema from the parse schema in `AiClient`; assemble advice with a total function after the strict ratings are settled; map failures to codes in one pure function; and replace both stores' persist wiring with one `createGuardedStorage` helper that owns set-aside, pruning, migration and an in-memory incident store. Ask the user for one cheap live smoke call (new schema accepted by Google) and, optionally, a short latency measurement; neither is needed to start building.

### Pattern 1: Strict ratings, lenient advice (the answer to Q3)

**What:** The model returns one JSON object. The client parses it with a schema whose `ratings` are strict (exactly one per requirement, valid enums) and whose `plans` and `tailoring` are `z.unknown()`. The provider is shown a different, strict schema. After `settle()` has produced the final ratings, `buildAdvice()` turns the unknown parts into a schema-valid `Advice`, item by item, and cannot throw.

**When to use:** Whenever part of a paid response is optional garnish and part is the product.

**Why not one schema:** `request.schema.safeParse(JSON.parse(text))` rejects the whole answer on the first bad advice item [VERIFIED: server/src/ai/client.ts:109-110]. `.catch()` / `.default()` would avoid that but emit a `default` key, which Gemini does not document and the allow-list test fails on [VERIFIED: scratch run: `CATCH {"...","default":[],...}`]. `z.unknown()` emits `{}` (no constraint) [VERIFIED: scratch run], so it must never be the provider schema.

### Pattern 2: One pure code-mapping function at the seam

`client.ts` already produces a closed-vocabulary diagnostic for every failure. Add one pure function `failureToErrorCode(diagnostic, deadlineFired): ErrorCode` and throw `new AppError(code)` instead of `new AppError('ai_failed')`. Route, request log and error handler stay unchanged (the log line `fit failed status=… category=…` already carries what ops need).

### Pattern 3: Guarded storage owns everything about bad data

`getItem` is the one place that sees the raw string, so it is the one place that can set aside correctly. It returns either a fully valid value at the current version, or `null` after reporting. Zustand's own `migrate` and `merge` are not used.

### Anti-Patterns to Avoid

- **Validating advice inside the provider-facing schema's parse path.** One bad plan costs the user a paid, otherwise good result.
- **Editing model text to "fix" it** (stripping a URL out of a sentence). Drop the item instead; an edited sentence can change meaning.
- **A test-only switch in the app server** (a header, query param or env flag a user could set). All failure injection lives in the stand-in (separate process) or in the browser test (`page.route`).
- **Reading the clock during render** for the progress text. Read it inside the interval callback.
- **Logging advice counts, raw storage values or Zod issues.** The server logs route, status, duration (plus the existing status/category failure line). The browser reports incident kind, store name and counts only.

### 1.1 What reaches the API (Q1)

The converter sends exactly what Zod emits, minus `$schema`, plus `propertyOrdering` on every object [VERIFIED: server/src/ai/schema.ts:44-48]. Re-checked this session with the proposed advice schema [VERIFIED: scratch run]:

| Zod authoring | JSON Schema that reaches Gemini | Use? |

| `z.enum([...])` | `type: "string"`, `enum` | Yes |

**Recommended wire schema** (new code; field order is the generation order, and the prompt must not state an order):

```typescript
// server/src/ai/prompts/fit.ts (proposed)
const ratingsSchema = (ids: [string, ...string[]]) => z.array(/* existing rating object */).min(ids.length).max(ids.length)

export function fitModelOutputSchema(ids: readonly string[]) {
  const [first, ...rest] = ids
  if (first === undefined) throw new AppError('internal_error')
  const idEnum = z.enum([first, ...rest])
  return z.object({
    ratings: ratingsSchema([first, ...rest]),
    plans: z
      .array(
        z.object({
          requirementId: idEnum.describe('A requirement rated partial or not_evidenced'),
          steps: z.array(z.string()).min(2).max(4).describe('2 to 4 short steps, one line each'),
          whyItMatters: z.string().describe('One or two sentences about why this matters for this job'),
          effort: z.enum(['days', 'weeks', 'months']),
        }),
      )
      .max(ids.length)
      .describe('One plan per requirement rated partial or not_evidenced; none for met'),
    tailoring: z.object({
      emphasise: z
        .array(z.object({ quote: z.string().describe('Copied word for word from the resume, at most 25 words'), advice: z.string() }))
        .max(5),
      keywords: z.array(z.string()).max(8).describe('Words from the job that the resume does not use'),
    }),
  })
}
// The parse schema: ratings strict, the rest accepted as-is and handled item by item in buildAdvice.
export const fitModelParseSchema = (ids: readonly string[]) =>
  z.object({ ratings: /* same strict ratings */, plans: z.unknown(), tailoring: z.unknown() })
```

`AiClient` change (proposed, small): `GenerateJsonRequest<T>` gains `wireSchema?: z.ZodType` ("what the provider is shown; defaults to `schema`"), and `client.ts` sends `toGeminiSchema(request.wireSchema ?? request.schema)`. Existing tests that call `toGeminiSchema(call.schema)` (analyze.test.ts) must read `call.wireSchema ?? call.schema`.

**Not live-verified:** whether Google accepts this exact nested shape (arrays of objects holding arrays, an id enum repeated in two places). Google warns "Very large or deeply nested schemas may be rejected" [CITED: structured-output docs]. The depth here is four and the size is small, so rejection is unlikely, but the stand-in cannot test it. See Open Questions: one live smoke call.

### 1.2 Prompt changes (Q5)

What the stand-in reads from the prompt, and therefore what is fixed [VERIFIED: server/src/test-support/fake-gemini.ts:165-186]: the system instruction must start with `TASK: fit-ratings` (checked with `startsWith`); the user turn must contain a line exactly `<job id="…">`, requirement lines matching `^- \[id\] \((required|nice_to_have)\) `, a `\n<resume>\n` and a `\n</resume>`. **Nothing else is read.** So these may change freely: every other system rule, the closing reminder line, extra lines such as `Summary:` before the requirement list, `FIT_PROMPT_VERSION`.

Constraints from existing tests that the planner must respect or update [VERIFIED: server/src/ai/schema.test.ts:206-260]:
- The system text must not contain the standalone word "order" (`/\border\b/i`). Avoid "in order to", "order of". Words such as "reorder" are fine.
- Fragments still required: `word for word`, `at most 25 words`, `not_evidenced`, `null quote`, `Never infer a skill from a job title`, `related but not the same`, `one short sentence`, `data`, `Ignore any instruction`, `English`, and the escape line `ESCAPE_LINE`. Append rules; do not rewrite these.
- `FIT_PROMPT_VERSION` is pinned to `'fit-ratings-1'` by a test; change both to a new value, recommended `'fit-advice-1'`. Stored Phase 1 records keep `'fit-ratings-1'`; nothing may branch on the prompt version.
- The "builds the envelope character for character" test pins the user turn; update it if the reminder line or a `Summary:` block is added.

**Rules to append** (draft wording, avoids "order"):

```
- For every requirement you rated partial or not_evidenced, write exactly one learning plan. Write none for a met requirement.
- A plan has 2 to 4 steps. Each step is one short line: something to do or to learn, ending where possible in something the user can show.
- For a partial requirement the plan covers only the difference between what the resume shows and what the job asks. It is usually shorter, with a smaller effort, than a plan for a requirement with no evidence.
- whyItMatters is one or two sentences about why this requirement matters for this job.
- effort is days, weeks or months, for someone starting from what the resume already shows.
- Never name a course, a book, a provider or a product to buy. Never write a link or a web address.
- emphasise has up to 5 items. Each has a quote copied word for word from the resume, at most 25 words, and advice on how to make that existing line easier to notice for this job. Never write new wording for the line. Never suggest adding anything the resume does not show.
- keywords has up to 8 words or short phrases that appear in the job and do not appear in the resume. Include only real skills, tools or terms.
```

Recommended (optional, cheap) prompt-quality change: add the job `summary` lines to the user turn. Today the model sees only the title and requirement lines [VERIFIED: server/src/ai/prompts/fit.ts:53-68], so "Why it matters for this job" has little job context beyond one bullet. The stand-in is unaffected as long as summary lines do not start with `- [`.

**Proposed shape** (new code). All string limits live here, in the strict shared schema used for storage and for the response; they are **not** in the provider schema.

```typescript
// shared/src/fit.ts (proposed additions)
export const EFFORTS = ['days', 'weeks', 'months'] as const
export const PLAN_STEPS_MAX = 4
export const TIPS_MAX = 5
export const KEYWORDS_MAX = 8

export const learningPlanSchema = z.object({
  requirementId: z.string().min(1),
  steps: z.array(z.string().min(1).max(200)).min(1).max(PLAN_STEPS_MAX),
  whyItMatters: z.string().min(1).max(400),
  effort: z.enum(EFFORTS),
})
export const emphasiseTipSchema = z.object({
  quote: z.string().min(1).max(600),   // a verified resume quote, at most 25 words
  advice: z.string().min(1).max(400),
})
export const tailoringSchema = z.object({
  emphasise: z.array(emphasiseTipSchema).max(TIPS_MAX),
  keywords: z.array(z.string().min(2).max(40)).max(KEYWORDS_MAX),
})
export const adviceSchema = z.object({
  plans: z.array(learningPlanSchema).max(10),      // 10 = the job schema's requirement maximum
  tailoring: tailoringSchema.nullable(),           // null = the tips part was unusable
})
// fitResponseSchema: advice: adviceSchema.nullable()
```

| `advice` | Meaning | UI |
|---|---|---|
| `null` | Made before this phase (every Phase 1 check) | D-E08 notice with Check again; gaps still shown, no plan-missing lines |
| object, `tailoring: null` | The model's tips part was missing or malformed | Tailoring section shows an "unavailable, check again" line (new copy, for the UI contract step) |
| object, `plans` shorter than the gaps | Some plans missing or rejected | Per-gap plan-missing line (fixed copy already in UI-SPEC) |
| object, empty `emphasise` or `keywords` | Model returned none, or all were dropped | "Nothing specific to emphasise for this job." / "No missing keywords found." (UI-SPEC) |

`plans` is an array keyed by `requirementId`, read through the existing `indexRatingsFirstWins` generic helper (it is typed `<T extends { requirementId: string }>` [VERIFIED: shared/src/fit/score.ts:26-34]) so a stored duplicate can never disagree with itself. Plans are displayed by iterating `job.requirements`, not by the array order.

**Gaps in the view (FIT-04).** Extend `buildFitView` (selectors.ts) rather than storing anything. It already joins each job requirement to its stored rating through `indexRatingsFirstWins` and splits `required` / `niceToHave` in posting order [VERIFIED: src/features/fit-analysis/selectors.ts:38-57]. ## Part 3: Keeping ratings when advice is bad (Q3) and code-side checks (Q4)

### 3.1 Where the lenient code sits

In `analyzeFit` (server/src/fit/analyze.ts), after `ratings = ids.map((id) => settle(...))` and before the final `fitResponseSchema.parse` [VERIFIED: server/src/fit/analyze.ts:85-102]. Three rules:

1. The strict part is unchanged: the parse schema keeps `ratings` strict, so a broken ratings array still fails as `ai_invalid_output` (nothing to save).
2. `buildAdvice` takes the **final** ratings (after quote downgrades), because a rating downgraded to `not_evidenced` is now a gap and a plan the model wrote for it is valid, while a plan for a requirement that is `met` is not.
3. `buildAdvice` never throws and its result is passed through `adviceSchema.safeParse` as the last step, falling back to `{ plans: [], tailoring: null }`. The final `fitResponseSchema.parse` can then never fail because of advice, so the user cannot lose ratings to it.

A truncated or non-JSON answer still loses everything, because the JSON cannot be parsed at all. That is why the cap is generous (Part 1.3) and why `ai_truncated` is a retryable code.

### 3.2 Assembly rules (all in `server/src/fit/advice.ts`)

| Input defect | Handling |
|---|---|
| `plans` not an array, or `tailoring` not an object | `plans: []`, `tailoring: null` respectively |
| Plan for an id the job does not have, or for a `met` requirement | Dropped |
| Two plans for one id | First wins (same rule as ratings) |
| Plan missing `steps`/`whyItMatters`/`effort`, wrong types, `effort` not in `EFFORTS` | Plan dropped |
| A step empty, longer than 200 chars, or containing a link | That step dropped; plan kept if at least one step remains |
| More than 4 steps | First 4 kept |
| `whyItMatters` empty, over 400 chars, or containing a link | Plan dropped |
| Gap with no plan after all of the above | Nothing stored; UI shows the plan-missing line |
| Tip with a quote that fails `verifyQuote` against the prepared resume | Tip dropped (D-E05) |
| Tip `advice` empty, over 400 chars, or containing a link | Tip dropped |
| More than 5 tips | First 5 kept (after dropping) |
| Keyword failing the filter below, or a duplicate (case-insensitive) | Dropped; first 8 survivors kept |

Judgement call recorded in the Assumptions Log: a plan with one surviving step is kept (the prompt asks for 2 to 4; losing the whole plan to a single bad step is worse for the user). Say so to the planner; if the user prefers strictness, change `min(1)` to `min(2)` in one place.

No new log lines. The server may return drop counts to a callback used only by the spike script (like `onUsage`), never to the request log.

### 3.4 Keyword filter (D-E06)

**Posting text, from the as-built job shape** [VERIFIED: shared/src/job.ts:59-68]: `title`, `summary` (1 to 3 strings) and `requirements[].text`. There are no responsibilities or benefits fields. Define posting text as title + summary + every requirement text (what the user can read on the page). The model currently sees only title and requirements, so any keyword it proposes from those is automatically in the posting; checking against the fuller text only makes the filter more permissive in the right direction.

**Resume text** is the prepared string (the one sent to the model), in both hyphenation readings from `buildResumeIndex` (`joined` and `separated`).

A prototype built on the existing normaliser passed these cases [VERIFIED: scratch run, resume "Built React/Redux apps with Node services and unit tests... full-\nstack", posting "Strong Node.js and C++ skills; CI/CD pipelines, GraphQL APIs, A/B testing, React and Redux, unit test, full-stack, Kubernetes, Terraform"]:

| Keyword | In posting | In resume | Kept |
|---|---|---|---|
| `Node.js` (resume says "Node") | yes | yes (".js" fold) | no |
| `C++` | yes | no | yes |
| `CI/CD` | yes | no | yes |
| `GraphQL` | yes | no | yes |
| `A/B testing` | yes | no | yes |
| `React` (resume has "React/Redux") | yes | yes (slash split) | no |
| `Redux` | yes | yes | no |
| `unit tests` (resume "unit tests", posting "unit test") | yes | yes | no |
| `full stack` (resume "full-\nstack") | yes | yes | no |
| `Go` (resume has Go, posting does not) | no | yes | no |

Method (words are compared in the normaliser's form, `normaliseForMatch`, which keeps `C++`, `C#`, `.NET`->`net`, `node.js`, `ci/cd` as single tokens [VERIFIED: scratch run and server/src/fit/quotes.ts:33,56-64]):
- Generate the keyword's forms: as written; with `/` replaced by a space; with a trailing `.js` removed; and each with the last word's plural added or removed.
- Generate the resume's and posting's forms: normalised text, and the same with `/` replaced by a space (so "React/Redux" contains "react").
- A form is "in" a text if it occurs at a word boundary (a start/end of text or a space), exactly the `isWordBounded` rule already in quotes.ts (not exported; export a small `occursAsPhrase(text, phrase)` from quotes.ts rather than copying it).
- Keep iff some form is in the posting and **no** form is in either resume reading.
- Also reject: shorter than 2 or longer than 40 chars after trim, more than 4 words, contains a link, duplicates.

Known limits: no stemming beyond the plural fold, no synonyms ("continuous integration" does not satisfy `CI/CD`). A keyword the filter wrongly keeps is shown with the fixed note "Add only if true for you."; a keyword wrongly dropped is simply not shown. Both are the safe direction. A bonus property: because keywords must occur in the (trusted, seed) posting text, an untrusted resume cannot inject an arbitrary word into this list.

## Part 7: Progress under the Compiler purity rules (Q10)

Facts [VERIFIED: scratch run]: ESLint (`react-hooks/purity`) rejects `Date.now()` in a component body with "Cannot call impure function during render", and accepts the same call inside a `setInterval` callback in an effect. Vitest fake timers drive such a component (`vi.useFakeTimers()`, `act(() => vi.advanceTimersByTime(5000))` moved the displayed value from 0 to 5, then 31) with no real waiting, because Vitest fakes `Date` as well.

Pattern: `FitProgress` is mounted only while a check is pending, so its state resets per check. It records the start time inside the effect and updates once per second from the callback. A pure function maps elapsed seconds to the line:

```typescript
// src/features/fit-analysis/FitProgress.tsx (proposed)
export function progressLine(elapsedSeconds: number): string {
  if (elapsedSeconds >= 30) return 'Still working. This can take up to a minute.'
  if (elapsedSeconds >= 10) return 'Writing your learning plan and tips'
  if (elapsedSeconds >= 4) return 'Comparing it with each requirement'
  return 'Reading your resume'
}
export function FitProgress() {
  const [elapsed, setElapsed] = useState(0)
  useEffect(() => {
    const startedAt = Date.now()            // read inside the effect, not during render
    const id = setInterval(() => {
      setElapsed(Math.floor((Date.now() - startedAt) / 1000))
    }, 1000)
    return () => { clearInterval(id) }
  }, [])
  /* render the status region: heading, progressLine(elapsed), reassurance */
}
```
Lines change at least 4 s apart (thresholds 4, 10, 30), which satisfies the UI-SPEC rule "at most every 4 seconds" for a polite live region. Counting ticks instead of reading the clock would under-count in a background tab (timers are throttled); reading `Date.now()` in the callback does not.

Testing without waiting: a table-driven unit test of `progressLine` (0, 3, 4, 9, 10, 29, 30, 120) and a component test with fake timers asserting the line changes at 4 s, 10 s and 30 s. In e2e assert only the first line and the reassurance while the stand-in is slow (3 s default `delayMs`); Playwright's `page.clock` (present in 1.64.0 [VERIFIED: node_modules/playwright-core/types/types.d.ts:5835]) could fast-forward but was not tried here.

The existing status region is always rendered and filled while checking; `Progress.Root` (Radix) with no `value` is the indeterminate bar [VERIFIED: FitPanel.tsx:94-112].

## Part 9: Saved data (Q11, Q12, Q13)

### 9.1 Zustand 5.0.15 `persist`, re-verified (Q11)

Read from `node_modules/zustand/esm/middleware.mjs:380-439` and exercised by 9 scratch cases [VERIFIED: scratch run]:

| Situation | What happens |
|---|---|
| Unparseable JSON with `createJSONStorage` | `getItem` throws inside a thenable; the rejection is swallowed in the final `.catch`; **no `console.error`**; the store keeps its initial state; **the corrupt string stays in `localStorage` until the next `set`, which overwrites it** (stored `{broken` became `{"state":{"n":1},"version":1}` after one write) |
| Stored `version` differs and **no `migrate`** | `console.error("State loaded from storage couldn't be migrated since no migrate function was provided")`; `merge(undefined, current)`; nothing is written back; the old value stays until the next write |
| Stored `version` differs and `migrate` exists | `migrate(state, storedVersion)` runs first, then `merge(migrated, current)`; the merged state is **written back immediately** (`setItem`) |
| Stored version **newer** than the code | `migrate` is called with the newer number (it saw `7` in the test); with no `migrate` it is dropped as above |
| Envelope with missing or non-numeric `version` | treated as the **current** version; no migrate; the state is used |
| Nothing stored | `merge(undefined, current)` is still called |
| Stored JSON that is not an envelope (`"abc"`, `[1,2]`, `{"foo":1}`, `null`, `5`) | `merge(undefined, current)`: indistinguishable from "nothing stored" |
| `localStorage.setItem` throws (quota) inside `set()` | **The exception propagates out of the store action** (in-memory state was already updated). In this app that is `saveAnalysis` inside `useCheckFit`'s `onSuccess`, so a full disk would turn a successful paid check into a mutation error |
| Custom `PersistStorage` whose `getItem` returns `{ state, version: <current> }` | Hydrates synchronously (state present right after `create`); `migrate` is not called; a `setItem` that catches its own errors makes `set()` safe (verified: no throw, in-memory state updated) |

Order: `getItem` -> (version check) `migrate` -> `merge` -> `set` -> (if migrated) write back. When hydration is synchronous (it is: `toThenable` runs the chain inline) the store is filled before the first render, so there is no loading flash and no `hasHydrated` gate [CARRIED: 01-RESEARCH.md D.1, consistent with the scratch hydration tests].

Conclusion: `merge` and `migrate` are the wrong place to detect corruption. Do it in `getItem`.

### 9.2 The shared helper `createGuardedStorage<S>(options)` (new, `src/lib/guarded-storage.ts`)

Options: `name`, `version` (current persist version), `migrations: Record<number, (state: unknown) => unknown>` (key n migrates n to n+1), `validate(state): { state: S; dropped: unknown | null; droppedCount: number } | null`, `keep` (default 3, D-E10), injectable `now` and `storage` for tests, and a `report` function defaulting to the incident store. It returns a `PersistStorage<S>` and the stores pass it as `persist`'s `storage` option; they drop their `merge` (the default shallow merge is correct for `{ byJobId }` and `{ resume }`) and add no `migrate`.

`getItem(name)`:
1. Read the raw string, catching a throwing/blocked `localStorage` (private mode, disabled): report `write_failed` (storage unavailable) once and return `null`; the app then runs in memory.
2. `null` raw: return `null` (first run).
3. `JSON.parse` fails: set aside the raw string, report `unreadable`, return `null`.
4. Not an object with an integer `version` and a `state` key: set aside the raw string, report `unreadable`, return `null`. (Do not treat a missing version as current, as Zustand would.)
5. `version > current`: set aside, report `newer`, return `null`. Never run an old reader over newer data.
6. `version < current`: apply `migrations[v]` for each step; a missing step or a throw means set aside + `unreadable`.
7. `validate(state)`: `null` means set aside the whole raw + `unreadable`. For the analyses store `validate` parses `byJobId` entry by entry with `storedAnalysisSchema` (and checks the key equals `entry.jobId`), keeps the good ones and returns the bad ones as `dropped`.
8. If entries were dropped or a migration ran, **rewrite the cleaned envelope to the original key immediately** (otherwise the same bad entries are found, set aside and reported again on every reload). For dropped entries set aside only the dropped ones, wrapped in the same `{ state, version }` envelope so Phase 7 can read the copy with the same reader; report `partial` with the count.
9. Return `{ state, version: current }`.

`setAside(text)`: key `"<name>:corrupt:<ISO timestamp>"` (for example `jw:analyses:corrupt:2026-10-11T14:52:33.836Z`; key style matches the as-built `jw:` colon names [VERIFIED: fit-store.ts:26, resume-store.ts:33]); write; if the write throws (quota) prune **all** older copies of that store and retry once; if it still fails, report `copyKept: false` and leave the original untouched. After a successful write, prune to the newest 3 by lexicographic key order (ISO timestamps sort correctly). Remove the original key only when the copy was kept (whole-value cases).

`setItem(name, value)`: `JSON.stringify` and write inside try/catch; on failure report `write_failed` (deduplicated per store) and return normally. `removeItem`: try/catch.

Nothing in the helper may log, `console.*`, or place a raw value, a Zod issue or a parse error message in an incident. An incident holds `{ id, store, kind, copyKept, dropped? }`.

Set-aside copies contain whatever the corrupt value contained (resume text the app saved is already contact-redacted; a hand-edited value may contain anything). They live in the same plaintext `localStorage` as the live data, are bounded to 3 per store (D-E10), and **Phase 7's "erase all" must remove every key starting with `jw:`, including `:corrupt:` copies**.

### 9.3 The incident store (non-persisted)

A tiny Zustand store in `src/lib/storage-incidents.ts`: `incidents: StorageIncident[]` (replaced immutably), `report(incident)`, `dismiss(id)`. `report` deduplicates `write_failed` per store so a full disk does not add a line per save. It is created when the module is imported, which happens before React renders because the stores' `getItem` runs at their module import; `<StorageNotice />` mounted at the top of `App` therefore shows incidents **from the first render**. Select the array (`useIncidentStore((s) => s.incidents)`); derive lines in render. Selectors that build a new array or object on each call loop under Zustand 5; select the stored reference and map in render.

Notice behaviour (Q13): dismissal is in memory only. The original corrupt value has already been moved, so a refresh finds nothing to complain about: the notice does not reappear after a refresh whether or not it was dismissed. The trade-off is that a user who refreshes before reading it never sees it; the copy remains in storage. I recommend this over persisting an "acknowledged" flag, because a persisted flag is one more thing that can corrupt. Incident kinds the UI contract must word: the four in UI-SPEC (`unreadable` for resume, `unreadable` for analyses, `partial`, `write_failed`) plus two the old contract does not have: `newer` (data written by a newer app version) and `copyKept: false` (the copy could not be written, so "A copy is kept in this browser." would be untrue).

### 9.5 Cross-tab and the Compiler (Q13)

There is no `storage` listener anywhere in `src/`, so there is no cross-tab behaviour to preserve. Do not add one: a listener would call `rehydrate()` and re-run `getItem`, which is safe with this design (set-aside removes the bad key, so it cannot be reported twice) but is scope the phase does not need. One cross-tab note: if two tabs are open and one sets data aside, the other still holds the old state in memory and its next save rewrites a clean key; no data is lost beyond the corrupt value already copied.

Compiler rules: stores are plain modules, no hook changes. Do not wrap anything in `useMemo`/`useCallback`/`memo`. Components read `analysis` and the view through selectors and derive gaps in render. New components use `useId` for label/description ids and take `ref` as a prop.

## Part 10: Security and privacy additions (Q16)

| Risk | Handling |
|---|---|
| Model-written free text shown to the user (steps, why, tip advice, keywords, rationale) derived from an untrusted resume and a trusted seed posting | Render as plain text only (React escapes); no `dangerouslySetInnerHTML`, no markdown, no `<a>`; length caps and link rejection in `buildAdvice`; a component test with an HTML payload |
| Links in model output | Rejected in code (items dropped), forbidden in the prompt; text-only rendering means a leaked URL would not even be clickable |
| Prompt injection through the resume steering tips | Tip quotes must verify against the prepared resume; keywords must occur in the trusted posting text, so an injected word cannot appear; the free-text `advice` cannot be machine-checked and is bounded by the fixed intro sentence and plain-text rendering |
| Error bodies or logs echoing prompt or resume | `AppError` messages are fixed per code; the diagnostic is a closed vocabulary (status number, category, class name from fixed lists); new detection of `API_KEY_INVALID` reads one fixed token and copies nothing; no new log lines are added in this phase |
| Set-aside copies holding resume text in `localStorage` | Bounded to 3 per store, never logged or shown, never uploaded; same trust boundary as the live data; erased by Phase 7 with the `jw:` prefix; the privacy copy ("saved only in this browser") stays true |
| Rate-limit evasion by retry loops | Unchanged: "Try again" is a click, `retry: false` and `networkMode: 'always'` stay; the app limiter (20 per minute) applies |
| New codes leaking provider internals | Codes and messages are from fixed tables; the browser looks up copy by code |

Server stays stateless: no `fs`, no stored bodies. The only logs remain the request line (method, path, status, duration) and the existing failure line (`fit failed status=… category=…`) [VERIFIED: server/src/fit/routes.ts:20-23].

## Common Pitfalls

### Pitfall 1: One bad plan loses the ratings
**What goes wrong:** the client parses the whole answer with the schema it sent; a single violated advice constraint becomes `schema_mismatch` and the user gets an error instead of a good result.
**How to avoid:** separate `wireSchema` from the parse schema; advice parts are `z.unknown()` in the parse schema and handled by `buildAdvice`.
**Warning sign:** a test where one plan has five steps and the response is a 502.

### Pitfall 2: `.catch()`, `.default()` or string `.max()` in the provider schema
**What goes wrong:** they emit `default`, `maxLength`; the allow-list test fails, and the API may reject or ignore them [VERIFIED: scratch run].
**How to avoid:** limits live in the shared strict schema and in `buildAdvice` only.

### Pitfall 3: The word "order" in the system instruction
**What goes wrong:** `schema.test.ts` forbids `/\border\b/i` (Google advises not stating field order) [VERIFIED: schema.test.ts:231-233].
**How to avoid:** avoid "in order to"/"order of" in new rules.

### Pitfall 4: Deadline and client abort look identical
**What goes wrong:** both are `AbortError`/`aborted` [VERIFIED: scratch run], so a timeout is reported as a generic failure.
**How to avoid:** keep the `AbortSignal.timeout` object and test `deadline.aborted && !request.signal.aborted`.

### Pitfall 5: A deadline longer than the browser timeout
**What goes wrong:** with the server deadline at 45 s and the client at 60 s the server answers first. If the deadline were raised above 60 s the browser would abort first and show "can't reach the server".
**How to avoid:** keep `deadlineMs` below `DEFAULT_TIMEOUT_MS` (60 s) and add a test that asserts the relation.

### Pitfall 6: Persist `merge` cannot see corruption
**What goes wrong:** `merge(undefined)` for both empty and garbage; the corrupt value is later overwritten silently [VERIFIED: scratch run].
**How to avoid:** all detection in the custom `getItem`.

### Pitfall 7: Bad entries reported again on every reload
**What goes wrong:** per-entry drop that does not rewrite the cleaned envelope re-detects the same entries each load.
**How to avoid:** rewrite the original key right after dropping or migrating.

### Pitfall 8: A throwing `setItem` fails a successful paid check
**What goes wrong:** quota error propagates from `saveAnalysis` to the mutation's `onSuccess` [VERIFIED: scratch run].
**How to avoid:** `setItem` catches and reports; test with a throwing `Storage.prototype.setItem`.

### Pitfall 9: Server down looks like an internal error
**What goes wrong:** the Vite proxy returns an empty 502, mapped to `internal_error` today.
**How to avoid:** non-envelope 5xx becomes `server_unreachable` (Part 5).

### Pitfall 10: Two "Check again" buttons and hidden collapsed content break tests
**What goes wrong:** strict-mode locator errors; `Collapsible.Content` renders nothing when closed.
**How to avoid:** distinct accessible names; open the trigger in tests; update the `advice: null` fixtures.

### Pitfall 11: The stand-in and the prompt drift
**What goes wrong:** the stand-in parses the envelope; a layout change that breaks its regexes makes it answer 400, which would look like a provider failure.
**How to avoid:** keep `TASK: fit-ratings` as the first line, keep the `<job id>` line, requirement line format and `<resume>` markers; update the pinned envelope test deliberately.

### Pitfall 12: e2e rate limit and shared stand-in
**What goes wrong:** more than 20 fit requests in a minute produce `too_many_requests`; parallel spec files flip the one global scenario.
**How to avoid:** put fit-calling tests in `check-fit.spec.ts`; the storage spec makes no fit call. Existing e2e expects `advice: null` after a real check [VERIFIED: e2e/check-fit.spec.ts:87-97] and must change to an advice object.

## Code Examples

### Failure to code (new `server/src/ai/failure-code.ts`)

```typescript
import type { ErrorCode } from '@jobs-workspace/shared'
import type { AiFailureDiagnostic } from './diagnose'

// Pure: a closed diagnostic in, a code out. Never sees a message, body or key.
export function failureToErrorCode(d: AiFailureDiagnostic): ErrorCode {
  if (d.category === 'timeout') return 'ai_timeout'
  if (d.category === 'blocked') return 'ai_blocked'
  if (d.category === 'unfinished') return 'ai_truncated'
  if (d.category === 'empty_text' || d.category === 'invalid_json' || d.category === 'schema_mismatch') {
    return 'ai_invalid_output'
  }
  if (d.category === 'network') return 'ai_network'
  if (d.httpStatus === 401 || d.httpStatus === 403) return 'ai_auth_failed'
  if (d.httpStatus === 402 || d.category === 'FAILED_PRECONDITION') return 'ai_billing'
  if (d.httpStatus === 429) return 'ai_rate_limited'
  if (d.httpStatus !== null && d.httpStatus >= 500) return 'ai_overloaded'
  return 'ai_failed'
}
```
