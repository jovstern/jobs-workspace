# Phase 1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope of this contract (read first)

Phase 1 proves the AI path on a **deliberately plain stub page**. The LinkedIn-like shell, palette, three-pane layout, search and the real design system belong to Phase 2 and are **not** designed here.

This contract therefore fixes, in this order of importance:

1. **Structure and states**: what is on the page, in the resume dialog and in the fit panel, and every loading, empty, error, not-configured, stale and corrupted-storage state.
2. **Interaction and accessibility**: focus, keyboard, announcements, what is disabled and why.
3. **Exact copy**: especially the user-fixed strings (CONTEXT.md "Specific Ideas") and the privacy note.
4. **Minimum visual tokens**: a small spacing and type scale and neutral Tailwind default colours, so the page is tidy but carries no design opinion Phase 2 must unpick.

Anything not in this file is the executor's call, but must stay inside the token tables below. Phase 2 restyles only through the seven shared presentational components named in "Phase 2 handoff", so this phase builds that thin layer on purpose.

Sources: CONTEXT.md D-05..D-13, D-17, D-18, D-09a; RESEARCH.md A.5 (error taxonomy), A.6 (data-use sentence), B.1..B.4 (ratings, score, "I do have this", stale), C.1 (PDF limits), C.3 (redaction), D.1..D.3 (storage notice, progress, two-step review); `.claude/skills/stack-conventions/SKILL.md`; root `CLAUDE.md`; `src/features/greeting/GreetingForm.tsx`.

## Spacing Scale

Declared values (multiples of 4). Tailwind classes map as `1=4px, 2=8px, 4=16px, 6=24px, 8=32px, 12=48px, 16=64px`. **Do not use `3`, `5`, `.5` steps** (12px, 20px, 2px-offsets) for padding, margin or gap.

| Token | Value | Tailwind | Usage |
|-------|-------|----------|-------|
| xs | 4px | `1` | Gap between a label and its control, glyph-to-text gap, chip inner gap |
| sm | 8px | `2` | Compact spacing: badge padding, gap between chips, input vertical padding |
| md | 16px | `4` | Default: input horizontal padding, button horizontal padding, gap inside a card section |
| lg | 24px | `6` | Card padding, dialog body padding, gap between page sections |
| xl | 32px | `8` | Page vertical padding, gap between the two page columns |
| 2xl | 48px | `12` | Gap before the first heading of a fit-panel section group |
| 3xl | 64px | `16` | Not used in this phase (reserved for Phase 2 page-level spacing) |

Exceptions (each is a fixed dimension, not a spacing step):

- **Primary and secondary buttons are `min-h-11` (44px)** so touch targets are comfortable at tablet width.
- **Chip remove button and the "×" glyph button are `size-6` (24px)**, the WCAG 2.2 AA minimum target (SC 2.5.8); chip height is 32px (`py-1` around the 24px button).
- Progress bar track `h-2` (8px). Borders 1px. Focus outline 2px with 2px offset.
- Layout widths: dialog `max-w-3xl` (768px); job list column `20rem` (320px) at `lg`; page container `max-w-5xl` (1024px).

## Typography

Exactly **four sizes** (14, 16, 20, 28) and **two weights** (400, 600). `font-medium` (500) from the greeting reference form is **not** used.

| Role | Size | Weight | Line Height | Tailwind | Used for |
|------|------|--------|-------------|----------|----------|
| Body | 16px | 400 | 1.5 | `text-base font-normal leading-normal` | Paragraphs, requirement text, input text, quotes |
| Small | 14px | 400 | 1.5 | `text-sm font-normal leading-normal` | Help text, meta lines, badges, chips, error text, resume textarea (with `font-mono`) |
| Label | 14px | 600 | 1.5 | `text-sm font-semibold leading-normal` | Field labels, badge text, button text in dense rows |
| Heading | 20px | 600 | 1.2 | `text-xl font-semibold leading-[1.2]` | Page `h1`, job title `h2`, fit panel `h2`, dialog title |
| Display | 28px | 600 | 1.2 | `text-3xl font-semibold leading-[1.2] tabular-nums` | The score percentage only |

Sub-headings inside a card or the fit panel (`h3`: "Required", "Gaps", "Learning plan") use **Body size at weight 600** (`text-base font-semibold`), not a fifth size. Buttons use Body size, weight 600.

Long text: all text wraps (`break-words`); nothing in this phase is truncated with an ellipsis. Quotes, rationales and job titles wrap to as many lines as they need.

## Color

Neutral Tailwind v4 default palette only. No custom hex values and no `@theme` colour tokens in this phase. Contrast ratios computed 2026-10-10 from the installed `tailwindcss@4.3.3` `theme.css` oklch values (WCAG 2.x relative luminance).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `gray-50` page background; `white` for any area that holds text | Page background, area behind the two columns |
| Secondary (30%) | `white` surfaces with `border-gray-200` | Cards, dialog, job list items, fit panel sections |
| Accent (10%) | `blue-700` (hover `blue-800`) | Listed below, nothing else |
| Destructive | `red-700` (hover `red-800`); tint `red-50`/`red-800` for error notices | Delete-resume confirm button, error notices |
| Text primary | `gray-900` | 17.7:1 on white, 17.0:1 on `gray-50` |
| Text secondary | `gray-600` | 7.6:1 on white, 7.2:1 on `gray-50`. Never lighter than `gray-600` |

Accent reserved for (explicit list):

1. The filled primary button (`blue-700` background, white text 6.8:1; hover `blue-800` 8.8:1). At most one primary button is visible per surface (page: "Check my fit"; each dialog view: its single forward action).
2. The keyboard focus outline on every interactive element (`outline-blue-700`, 2px, offset 2px), except the destructive button, whose outline is `outline-red-700`.
3. The selected job in the job list (left border 4px `blue-700` plus `blue-50` background, text stays `gray-900`; 16.3:1).
4. The active tab indicator in the intake tabs (bottom border 2px `blue-700`).
5. Text links and text-style buttons such as "Remove confirmation" (`blue-700`, underlined; 6.8:1 on white).
6. The Progress bar fill.

Accent is **not** used for score, band, rating or status colours.

**Status tones** (semantic, always paired with a text label, never colour alone; each pair meets 4.5:1):

| Tone | Foreground on background | Ratio | Used for |
|------|--------------------------|-------|----------|
| success | `green-800` on `green-50`, border `green-200` | 6.8:1 | Rating "Met"; band "Strong fit" |
| teal | `teal-800` on `teal-50`, border `teal-200` | 7.2:1 | Band "Good fit" |
| caution | `amber-900` on `amber-50`, border `amber-200` | 8.8:1 | Rating "Partial"; band "Stretch"; the stale marker "resume changed, re-check?"; "confirmed by you" marker |
| neutral | `gray-800` on `gray-100`, border `gray-200` | 13.3:1 | Rating "Not evidenced"; band "Long shot"; neutral notices |
| danger | `red-800` on `red-50`, border `red-200` | 7.7:1 | Error notices only |

Why neutral and caution for the low end: "Not evidenced" and "Long shot" are information, not failure, and the score is "never a verdict on whether to apply" (D-11). Red is reserved for errors and the destructive confirm.

Dark theme: not supported. Do not add `dark:` variants.

### Privacy note (DATA-06, D-02, D-17, D-18)

Component `PrivacyNote`, heading `h2` "How your resume is used" (Heading size on the page card, Label weight inside the dialog). Shown **in full, always visible**, in the resume card on the page and in the dialog's intake view. Not collapsed.

> This app's server reads your resume only to pull the text out of a PDF and to pass it to Google's Gemini AI. It does not store or log your resume.
>
> To analyse it, the app sends your resume text to Google's Gemini AI, with email addresses, phone numbers, street addresses and links removed where we can recognise them. Google processes the text to produce the analysis.
>
> On Google's paid tier, Google says it does not use this content to improve its products. It keeps logs of requests for a limited time, only to detect abuse and meet legal obligations.
>
> Your resume, profile and fit checks are saved only in this browser.

Rules: (1) all four sentences' claims stay; the caveats ("where we can recognise them", "Google says", "limited time", "only to detect abuse and meet legal obligations") may not be shortened away. (2) The third paragraph is true only while the key's Google project has an active billing account (RESEARCH A.6, Pitfall 11): it ships only after the pre-ship human check that the key is on a billed project; if that check fails, delete that paragraph and nothing else. (3) The PDF-fallback consent copy above is the only other place the file-level exposure is stated.

### Errors (FIT-11, RESEARCH A.5)

Branch on the typed `code`, never on message text. A `role="alert"` notice (danger tone) shows a heading, the message, and actions. Retryable codes get a **Try again** button (same request, one click, never automatic); non-retryable codes show no retry button (the page's own action stays available). A failed re-check keeps the previous result visible below the notice.

Headings: fit check "Could not check your fit"; profile "Could not build your profile"; PDF read "Could not read your file".

| `code` | Message | Extra action |
|--------|---------|--------------|
| `ai_not_configured` | AI is not set up. Add GEMINI_API_KEY to server/.env and restart the server. | none (retry hidden) |
| `ai_auth_failed` | Google did not accept the AI key. Check GEMINI_API_KEY in server/.env and restart the server. | none |
| `ai_billing` | The Google project behind the key has no credit or billing set up. Fix it in Google AI Studio, then try again. | none |
| `ai_rate_limited` | Google's AI is rate limiting this key. Wait a minute, then try again. | Try again |
| `ai_overloaded` | Google's AI is busy right now. Try again in a moment. | Try again |
| `ai_timeout` | The request took too long. Try again. | Try again |
| `ai_network` | Could not reach Google's AI. Check your connection and try again. | Try again |
| `ai_blocked` | The AI declined to process this text. Edit your resume text and try again. | Edit resume (opens Step 1) |
| `ai_truncated` | The AI's answer was cut off. Try again. | Try again |
| `ai_invalid_output` | The AI returned something we could not use. Try again. | Try again |
| `too_many_requests` | Too many requests in a short time. Wait a minute, then try again. | Try again |
| `server_unreachable` | Can't reach the app server (is it running?) | Try again |
| any other / `validation_error` | Something went wrong on our side. Try again. | Try again |

Profile build failure adds a second action, **Fill in my profile by hand**, which opens Step 2 with an empty profile so the user is never blocked by the AI being down. This includes `ai_not_configured`.

| Write failed (quota or blocked) | Your browser could not save your latest changes. Storage may be full. What you see now will be lost when you refresh. |

## Layout and Structure

Structure is the contract; component names are suggestions (one component per file, named export, per stack rules). Seven shared presentational components live in `src/components/` (see "Phase 2 handoff"); feature components live in their feature folder.

### Page (replaces the greeting form in `src/App.tsx`)

```
StorageNotice                       (only when there is an incident)
header   h1 "Jobs Workspace" + subtitle
section  Resume card                (ResumeCard: status, actions, PrivacyNote)
section  grid:  [ Jobs list ] [ Job detail: posting + fit region ]
```

- Container: `mx-auto max-w-5xl px-6 py-8` on a `bg-gray-50` page; sections separated by `gap-6`.
- At `lg` (1024px) and up: two columns `grid-cols-[20rem_1fr] gap-8`. Between 768px and 1023px: one column, jobs list first, rendered as a 2-column grid of buttons so ten jobs stay short. Below 768px is not supported (desktop and tablet only); the page must not scroll horizontally but needs no mobile layout.
- Each region is a `Card` (`rounded-lg border border-gray-200 bg-white p-6`). Heading hierarchy: `h1` page, `h2` per region (Resume card has the privacy `h2` inside it), `h3` inside the job detail and fit panel.
- Landmarks: `header`, `main`, and each region a `section` with `aria-labelledby` pointing at its `h2`.

### Resume card

| State | Content |
|-------|---------|
| No resume | `h2` "Your resume", empty copy, secondary button **Add your resume**, `PrivacyNote` |
| Resume present | `h2` "Your resume", line `Resume saved. {n} characters, {s} skills, {r} roles.` (Small, `tabular-nums`), buttons **Review resume**, **Replace resume**, **Delete resume** (all secondary), `PrivacyNote` |
| Live region | A visually hidden `role="status"` announces "Resume saved." after a save |

### Jobs list

- `h2` "Jobs" and a `ul` of 8 to 10 `button`s (`li > button`, no table, no listbox role). Each shows: title (Label weight, wraps), then `{company} · {level} · {location}` (Small, `gray-600`), then `Checking fit` when that job's mutation is pending.
- Selected state: `aria-current="true"`, left border 4px `blue-700` and `bg-blue-50`. Not selected: `border-l-4 border-transparent hover:bg-gray-50`.
- No job is selected on first load. The selection is component state only (Phase 2 moves it to the URL); it is not persisted.
- No scores, viewed marks or filters on list rows (FIT-09 and search are Phase 2).

### Job detail (selected job)

1. `h2` job title (Heading); meta line (Small, `gray-600`).
2. Summary paragraph(s) (Body).
3. `h3` "Required" with the required requirements as a `ul`; `h3` "Nice to have" with the nice-to-haves (D-15: hand-authored, shown here exactly as the model will rate them).
4. Action row: primary **Check my fit** when no analysis exists for this job. Beside it, Small `gray-600` text states why it is unavailable if it is (not configured, health unreachable). When an analysis exists the action moves into the fit panel header (**Check again** or **Re-check**) and this row shows nothing.
5. Fit region directly below (`FitPanel`), one of: none, running, error, result, stale result. It is the only part of the page that changes while a request is in flight, and it has `aria-live="polite"` only on its status line, never on the whole result.

### Fit panel (result), top to bottom

1. Header row: `h2` "Your fit for {job title}"; right side the re-run button (secondary): **Check again** (fresh) or **Re-check** (stale).
2. **Stale marker** (only if stale): caution badge **resume changed, re-check?** and the stale helper. The old result stays fully visible and readable below.
3. **Score block**: caption, `{score}%` (Display) and the band badge on one baseline row, then the required count, the confirmed split (if any), the disclaimer, the checked line.
4. **Requirements** (`h3`): all requirements in two groups (Required, Nice to have) as an ordered list in posting order. Each item: requirement text; rating badge; for met/partial the quote in a `blockquote` (Small, `border-l-2 border-gray-300 pl-4`) preceded by "From your resume:"; the model's one-sentence rationale (Small, `gray-600`); for a confirmed credit the **confirmed by you, not in your resume** marker, the tip, and a **Remove confirmation** text button; for a rejected quote the rejected-quote sentence.
5. **Gaps** (`h3` "Gaps", tabIndex -1 for focus return): two sub-groups, `Required gaps ({n})` then `Nice-to-have gaps ({n})`, each an ordered list. A gap is any requirement whose effective rating is not met. Each gap item contains: the requirement text; the gap phrase (**not evidenced in your resume** or *partly evidenced in your resume*); the **I do have this** button; and the learning plan block (What to learn, Why it matters for this job, Rough effort) or the plan-missing line. "Gaps" is a task list, so each item carries its own button and plan rather than a separate "Learning plan" section.
6. **Tailoring** (`h3` heading, intro, Emphasise list, Keywords chips with the note).

Order within Requirements and Gaps follows the posting. Gaps are never sorted by importance (no model-made ranking).

### Resume dialog (`Modal`, Radix Dialog)

- Centered, `w-full max-w-3xl`, `max-h-[calc(100dvh-4rem)]`, overlay `bg-gray-900/50`, white content, header (title, description, close `×`), scrolling body, fixed footer. The footer order is secondary left, primary right. No open/close animation in this phase.
- One `Dialog.Title` and one `Dialog.Description` on every view (Radix requirement). Description is one sentence of the help copy for that view.
- Views, in `useState` inside `ResumeDialog`, each its own component: **Intake** (tabs: PDF, Paste, plus the consent, error and reading states and `PrivacyNote`), **Step 1** (text), **Step 2** (profile). Intake is not numbered; the two review steps are "Step 1 of 2" and "Step 2 of 2" (D-05).
- Flow, first time or replace: Intake, then Step 1, then Step 2, then Save. Flow, review: opens at Step 1.
- D-08 interpretation: the question is asked when the user leaves Step 1 with changed text and a profile already exists. Yes shows the profile build, then lands on Step 2 with the rebuilt profile (confirmed skills kept). No lands on Step 2 with the existing profile. If the text is unchanged Step 1 goes straight to Step 2 with no question and no request.
- Closing (Esc, `×`, overlay click) with an unsaved draft asks "Discard this resume draft?". Closing a view with nothing entered closes silently.
- When opened from **Check my fit** with no resume, Step 2's save button reads **Save and check my fit**, and saving closes the dialog and starts the check for the job that was selected (RES-05). The job id is held in component state.

### Step 1 (text)

`h3`-level step heading (Body 600 inside the dialog; the dialog title is the `h2`/Heading), help line, source note, redaction notice, placeholder note, then a `textarea` (label "Resume text", `font-mono text-sm`, `min-h-64`, vertical resize only). Built with TanStack Form and `z.string().trim().min(50).max(60000)`, markup identical to `GreetingForm` (label `htmlFor`, `role="alert"` error, `aria-invalid`, `aria-describedby` pointing at both the help text and the error). The redaction function runs on every text entering this step, so the visible text equals what will be sent.

### Step 2 (profile)

Fields in order: Headline (text, max 120), Years of experience (`type="number"`, `inputMode="numeric"`, 0 to 60), Skills (chip group), Roles (repeating fieldset).

- **Skills**: `ul` of chips. A chip is `rounded-full border bg-white py-1 pl-2 pr-1 text-sm`; resume-sourced chips use a solid `border-gray-300`, user-confirmed chips a dashed `border-gray-400 border-dashed`. Each chip ends in a `×` button (24px) with accessible name `Remove {skill}`; a confirmed chip also contains `VisuallyHidden` text ", confirmed by you, not in your resume". Add field: text input plus **Add skill** button; **Enter** in the input adds the skill and does not submit the form. Limits: 60 skills, 40 characters each, no case-insensitive duplicates. Chips wrap (`flex flex-wrap gap-2`).
- **Roles**: each role is a `fieldset` with a `legend` (the role title or "New role"), fields Job title (max 80), Company (max 80), Start (max 20), End (max 20, help "Write Present for a current role."), One-line summary (max 200, single-line input). Stable ids as keys (never indexes). **Add a role** appends one and moves focus to its Job title input; **Remove role** deletes it from the draft and moves focus to the next role's remove button, or to **Add a role** if it was the last. Limit 15 roles.
- All limits are defaults for the shared Zod schema; the planner may adjust them with the schema, but each must keep the "Use {n} characters or fewer." error.

### Fit running

Replaces the result area with a `Card` containing: `h2` "Checking your fit"; Radix `Progress` with no `value` (indeterminate) and `aria-label="Checking your fit"`, fill `bg-blue-700 w-full animate-pulse motion-reduce:animate-none` inside a `h-2 rounded-full bg-gray-200` track; the stage line and reassurance in a `role="status"` region. No cancel in Phase 1 (the server deadline bounds the call). The primary button is `aria-disabled` while pending and its text stays "Check my fit" (do not swap in a spinner or change the label, so the accessible name stays stable). One request per job at a time; selecting another job during a request is allowed and its own panel is independent.

## Interaction and Accessibility

| Topic | Contract |
|-------|----------|
| Keyboard | Everything reachable by Tab in reading order; no custom key handlers except: Enter in the "Add a skill" input adds a chip; Esc closes dialogs (AlertDialog Esc = Cancel); arrow keys inside Tabs (Radix default). No drag, no hover-only controls. |
| Focus indicator | 2px `blue-700` outline with 2px offset on every focusable element; never removed. |
| Focus management | Radix handles trap, return-to-trigger and initial focus. Initial focus: Intake, the active tab; Step 1, the textarea; Step 2, the Headline input; AlertDialogs, the safe/cancel button. On step change, focus moves to the new step heading (`tabIndex={-1}`). After **I do have this** the gap row disappears: focus moves to the next gap's **I do have this** button, or to the "Gaps" heading when none are left. After **Remove confirmation**, focus moves to the new gap's button for that requirement if it appears, else to the "Requirements" heading. After a successful check, focus stays on the re-run control; the live region announces completion. |
| Announcements | Only these live regions: the fit status line (`role="status"`: "Checking your fit" stages, then "Fit check complete. Fit estimate {n}%, {band}."), the "I do have this" message, "Resume saved.", the profile-build status, and the consent/status panel. Errors use `role="alert"`; `StorageNotice` uses `role="alert"`. Stage lines change at most every 4 seconds. |
| Labels | Every control has a visible label tied by `htmlFor`/`id` (or `useId`). Label text is in the accessible name for every button (label-in-name): "I do have this: {text}" starts with the visible text. Glyphs (`✓ ◐ ○ ×`) are `aria-hidden`; the word beside each carries the meaning. |
| Colour | Never the only signal: rating, band, stale and confirmed states each have text; confirmed chips also have a dashed border; the selected job has `aria-current`. |
| Forms | `GreetingForm` pattern exactly: `noValidate`, validation on submit with the Zod schema, `role="alert"` error under the field, `aria-invalid` and `aria-describedby`. Fields inside the dialog submit on the step's forward button (a real `<form>` per step). |
| Disabled | Unavailable actions use `aria-disabled="true"` plus visible explanation text referenced by `aria-describedby`, not the `disabled` attribute, so they stay discoverable; the click handler does nothing. Gray style: `bg-gray-200 text-gray-700 cursor-not-allowed`. |
| Cost safety | AI requests start only from an explicit click on **Check my fit**, **Check again**, **Re-check**, **Build my profile**, **Yes, update profile**, **Let Google's AI read the whole file** or **Try again**. Never on mount, focus, selection, reopen, retry-by-timer or reconnect. Opening a job with a saved analysis shows it instantly with no request (FIT-08). |
| Motion | Only the indeterminate bar's `animate-pulse`, disabled under `prefers-reduced-motion`. |
| Text rendering | Resume text, quotes, rationales and plan text from the model are rendered as plain text. No `dangerouslySetInnerHTML`, no markdown rendering. |
| Windows | Tablet and desktop only. At 768px the dialog has 32px margin each side and scrolls its body. |

## Phase 2 handoff: what Phase 2 restyles, replaces and keeps

**Built on purpose as the only styling seam.** These seven files in `src/components/` hold all colour, border, radius and spacing classes for repeated chrome. Phase 2 swaps the class strings inside them (and adds `@theme` tokens in `src/index.css`) without touching any feature component:

| Component | Wraps | Variants this phase needs |
|-----------|-------|---------------------------|
| `Button` | `<button>` | `primary`, `secondary`, `destructive`, `link`; `aria-disabled` style |
| `Badge` | `<span>` | tones `success`, `teal`, `caution`, `neutral`, `danger` |
| `Chip` | `<li>` with remove button | `resume` (solid), `confirmed` (dashed) |
| `Card` | `<section>`/`<div>` | one surface |
| `Notice` | `<div>` with `role` | tones `neutral`, `caution`, `danger`; `status` or `alert` |
| `Modal` | Radix `Dialog` | header, scrolling body, footer; enforces Title and Description |
| `ConfirmDialog` | Radix `AlertDialog` | normal and destructive confirm |

Class strings to start from (all values from the tables above):

- `Button` base: `inline-flex min-h-11 items-center justify-center rounded px-4 py-2 text-base font-semibold focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-blue-700`. `primary`: `bg-blue-700 text-white hover:bg-blue-800`. `secondary`: `border border-gray-300 bg-white text-gray-900 hover:bg-gray-50`. `destructive`: `bg-red-700 text-white hover:bg-red-800 focus-visible:outline-red-700`. `link`: `min-h-0 px-0 py-0 text-sm text-blue-700 underline hover:text-blue-800`.
- Text input and textarea: `rounded border border-gray-300 bg-white px-4 py-2 text-base text-gray-900`.
- `Badge`: `inline-flex items-center gap-1 rounded-full border px-2 py-1 text-sm font-semibold` plus the tone pair from the status table.

**Phase 2 is expected to restyle** (free to change, no contract impact): palette and `@theme` tokens, font stack, radii, borders, shadows, the page shell, the Resume card's placement (it becomes a rail/drawer or a section of the detail pane), the two-column grid (replaced by the three-pane layout), the jobs list rows (replaced by result cards), the wordmark and header, band colours, and dialog sizing and animation.

**Phase 2 should keep** (these are behaviour and truth, verified by Phase 1 tests): all VERBATIM strings; the privacy note content; two-step review and the consent-first PDF flow; the structure of the fit panel (score block, requirements, gaps with plan and **I do have this**, tailoring); the stale marker and its rule; every state in the error table; focus and announcement rules; the rule that AI requests only start from an explicit click; plain-text rendering of model output.

**Phase 2 will replace, not restyle:** the page layout, the job picker (search replaces it), and URL-held selection (replaces component-state selection).
